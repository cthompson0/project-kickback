## 1. Executive release verdict

## **GO**

v0.7.0 is packaged, verified, and ready for the owner to submit when they choose.

The pre-bump audit found **no unexpected product functionality**, **no new
Twitch scopes**, **no M3D/M3E implementation**, and **no new Firefox data
category**. Every known-debt harness matched its recorded baseline, and one
improved. The
Mozilla validator reports **0 errors** with the same three documented warnings
the accepted v0.6 candidate carried.

Six things worth the owner's attention:

- **The zero-data boundary is proven structurally, not by query.** No shipped or
  submitted v0.6 artifact contains `channel_dwell_ended` or `experiment_arm` —
  verified by extracting all three and grepping. No production or private-beta
  client is *capable* of emitting either event, which is a stronger guarantee
  than a row count (§8).
- **The experiment SALT had no regression guard.** It was unchanged, but nothing
  would have failed if it had been. That was the one gap the brief explicitly
  asked to close, and it is now closed with golden assignments (§9).
- **The Firefox dev package and the AMO candidate are byte-identical** —
  `a7ec9436…` for both. Same content, deterministic ZIP. That is a free
  reproducibility signal and it is recorded rather than left as a coincidence.
- **The changelog gate caught a missing release entry.** `releaseVersion.test.tsx`
  requires `CHANGELOG.md` to describe the shipped version; bumping to 0.7.0
  without an entry failed it. That is the repository's own release process
  working, and it is why the audit is run rather than assumed (§15).
- **Chrome packaging is not byte-reproducible; Firefox is.** A deliberate
  asymmetry, explained in §12 — reproducibility was built where AMO requires it.
  The Chrome SHA256 identifies *this build*, not a reproducible identity.
- **`test:authz` improved from its baseline: 14/18 → 18/18, exit 0.** A delta
  in the improving direction, investigated and confirmed genuine (§14).

The only non-documentation changes are the version bump, one test file, and the
changelog entry. **No product code was touched** (§15, §16).

**Tagging is deferred.** The repository has **no git tags at all** — there is no
established tagging convention to follow, and the brief forbids inventing one
(§29).

## 12. Chrome / Firefox source parity

Both artifacts were built from **one working tree** in a single session, with no
source edit between the two packaging runs. The only difference is the
browser-specific manifest the adapter is designed to produce.

### Firefox is byte-reproducible; Chrome is not

Measured rather than assumed — each packager was run twice on unchanged source:

| Package | run 1 | run 2 | Reproducible |
|---|---|---|---|
| `Watchside-Firefox-v0.7.0.zip` | `a7ec9436…` | `a7ec9436…` | ✅ **yes** |
| `Watchside-Store-v0.7.0.zip` | `86fca76e…` | `a8eefb84…` | ❌ **no** |

**This is deliberate, not a defect.** Both packagers share `scripts/zip.mjs`,
whose `writeZip` defaults to the wall clock for entry timestamps.
`package-firefox.mjs` pins a fixed timestamp — its own comment says *"Without
this the ZIP is not reproducible"* — because AMO requires the source archive to
rebuild the candidate byte-for-byte. `package-beta.mjs` does not, because the
Chrome Web Store requires no such correspondence.

**Consequences, stated plainly:**

- The **Firefox** SHA256 is a reproducible identity. Anyone can rebuild it.
- The **Chrome** SHA256 identifies **this specific build** and will differ on
  the next run even with identical source. It is still a valid integrity check
  of the file being uploaded — it is simply not a reproducibility claim, and
  this report does not make one.

Recorded as an **M4.5 consolidation candidate**: both packagers could share the
fixed timestamp. Not changed here, because release tooling is not the thing to
refactor while cutting a release.

### Source parity

Both artifacts were built from **one working tree** in a single session, with no
source edit between the two packaging runs. The only difference is the
browser-specific manifest the adapter is designed to produce, and
`Watchside-Firefox-v0.7.0.zip` is byte-identical to the AMO candidate.

## 15. Bugs found and fixed

**No product defect was found.** One **release-process gate failed and was
satisfied**, which is a different thing and is recorded rather than glossed.

### The changelog gate

After bumping to 0.7.0, `npm test` failed:

```
tests/extension/releaseVersion.test.tsx
  › the changelog describes the version being shipped › has an entry for the current version
  AssertionError: expected '# Changelog…' to contain '## 0.7.0 —'
```

`CHANGELOG.md` is user-facing — *"written for the people using it"* — and the
repository enforces that every shipped version has an entry. Bumping without one
is exactly what the gate exists to catch.

**Fix:** added a `## 0.7.0 — Measuring whether any of this works` entry. It is
honest about what this release is: almost nothing looks different, and the one
thing users should know is that **Watchside now records how long you watch**,
that concurrent streams are counted separately, that background streams count,
and precisely what is never recorded. It also states that **no new Twitch
permission is requested**, because a user who sees a version bump deserves to
know that.

No test was weakened. The gate was satisfied by doing the thing it asks for.

**Repackaging consequence:** the Chrome package was rebuilt afterwards. The
Firefox candidate and source archive hashes were **unchanged** — `CHANGELOG.md`
is not in the source archive (verified: zero matches), and the extension package
contains only manifest, scripts, popup and icons.

### No product defect

The pre-bump audit checked each item the brief named — focus-gated dwell,
single-focused-channel metadata, concurrent accrual, attribution leakage,
bounded `observation_lost`, `stream_ended` distinguishability, repeat-creator
foundation, SALT stability, multi-destination, Stream Rooms, Gravity, JOIN,
auth — and every one was already correct in `main`.

The single code-adjacent change is the **SALT regression guard** (§9), which the
brief explicitly requested. It adds a test and touches no product code.

**No opportunistic refactors were performed.** The Chrome non-determinism in
§12 was left alone deliberately: it is not release-blocking, and release tooling
is not what to change while cutting a release.
