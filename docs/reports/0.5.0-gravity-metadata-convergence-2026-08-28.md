## 1. Observed failure

Reported from real browser use, after the enrichment fix landed:

- the correct multi-destination cards render;
- proper Twitch metadata **does** appear — but **inconsistently**: sometimes
  delayed, sometimes some destinations enrich while others stay bare, sometimes
  a stream gets nothing until a refresh;
- **refreshing makes the missing metadata appear.**

Data model correct, card pipeline correct, metadata content correct on arrival.
**Arrival is the defect.**

That description is precise enough to be diagnostic on its own: *"correct when
it arrives, and a refresh fixes it"* means the request is never made, not that
the response is wrong. It was never made.

## 2. Bootstrap lifecycle (the path that works)

```
sign in
  → auth signed_in
  → friends.refresh()          → friends.subscribe fires
      → scheduleDestinationsRefresh()
      → refreshAttention()  →  wantMetadata()   ← asks Twitch
      → updateTogether()
  → refreshFriendDestinations()  → friendDestinations populated
  → broadcast()
```

Two triggers fire close together, and `wantMetadata()` runs **with whatever
destinations exist at that moment**. On a reload the destination read and the
friends load both happen within a second or two of each other, so by the time
some later `refreshAttention()` runs — the next friend heartbeat, at most 45s —
the full set is present and everything is requested.

**Bootstrap does not do a "full sweep" that incremental updates skip.** It runs
the same `wantMetadata()`. It works because of *ordering luck*, not because of
a different mechanism — which is exactly why a refresh appeared to be a cure and
why the failure looked intermittent rather than absolute.

## 3. Incremental lifecycle (the path that fails)

A friend opens a second stream:

```
t=0     friend's report_destinations write also bumps presence.last_seen_at
t=0     → realtime presence event reaches the observer
t=0     → onPresence:
             friends.applyPresence(...)  → setState → friends.subscribe
                                         → refreshAttention() → wantMetadata()
                                            ▲ runs HERE, with the OLD set
             scheduleDestinationsRefresh()   (coalesced 1s)
t=1s    → refreshFriendDestinations()
             friendDestinations = {a: [lirik, teamliquid, timthetatman]}
             broadcast()
             ▲ three cards render. NOTHING asks about the two new channels.
t=45s   → the friend's next heartbeat → presence event → friends.subscribe
             → refreshAttention() → wantMetadata()
             ▲ NOW the set is complete, so the two are finally requested
t=45s+  → responses land → metadata onChange → broadcast → cards enrich
```

## 4. The exact divergence

> **The enrichment trigger fires about one second BEFORE the data it depends
> on arrives, every single time. Nothing fires after.**

`refreshFriendDestinations()` was the only place `friendDestinations` ever
changed, and on change it did exactly two things:

```ts
friendDestinations = next
broadcast()
```

It told the panel. It did not tell the metadata service. Every other trigger for
`wantMetadata()` is about something else entirely:

| Trigger | Fires when |
| --- | --- |
| `pushActivity()` | the **viewer's own** tab activity changes |
| `friends.subscribe` | a friend is added, removed, blocked — **or any presence event** |
| `groups.subscribe` | a group roster changes |
| the 30-minute alarm | (refreshes destinations, still no `wantMetadata`) |

**None of them is "a friend opened another stream".** The one that incidentally
rescues it is the friend's own 45-second presence heartbeat, arriving through
`friends.applyPresence` → `setState` → `friends.subscribe` → `refreshAttention`.

That single fact explains every symptom:

| Symptom | Cause |
| --- | --- |
| delayed | waits for the next heartbeat — up to 45s |
| some enrich, others do not | destinations added in stages each wait for their own next heartbeat |
| never until refresh | if the heartbeat's presence payload is unchanged, `applyPresence` still fires — but a friend going idle, a dropped socket, or a coalesced event can leave no trigger at all |
| refresh fixes it | bootstrap runs the same call with the set already complete |

## 5. Race and freshness issues found

### Defect A — the missing trigger (primary)

§4. A changed destination set did not ask for enrichment.

### Defect B — a concurrent read was dropped, not queued

```ts
if (destinationsPending) return
```

Single-flight that **discards** the second request. If a presence event arrived
while a destination read was in flight — likely, since the coalesce window is
1s and the RPC is a network round trip — `scheduleDestinationsRefresh()` fired
its timer, `refreshFriendDestinations()` returned immediately, and **the timer
was already cleared**. That change was then lost until some later unrelated
event asked again. This is the second half of "sometimes it just does not
update".

Fixed by remembering the request and re-running once the in-flight read
finishes.

### Answers to the specific questions asked

| # | Question | Answer |
| --- | --- | --- |
| 1 | Does `wantMetadata()` request newly missing channels as the set grows? | It does **now**. It did not, because it was never called on that event. |
| 2 | With A cached and B/C missing, are B/C definitely fetched? | Yes — `want()` filters by `needsRefresh` per channel. Verified by test. |
| 3 | Are concurrent requests deduped by channel? | **Yes.** `inFlight` is a `Set<login>`; one request cannot suppress an unrelated channel. Verified. |
| 4 | Does a completed fetch trigger a broadcast? | **Yes** — `onChange: () => { pushActivity(); updateTogether(); broadcast() }`. |
| 5 | Does the panel receive it when destinations did not change? | **Yes** — the broadcast is a full state snapshot. |
| 6 | Does React rerender when only metadata changes? | **Yes.** |
| 7 | Is metadata mutated in place, defeating reference equality? | **No.** `records = { ...records }` on every write, and `currentState()` spreads the snapshot again. |
| 8 | Is the trigger source still the singular channel? | **No** — fixed last commit; `gravityChannels` is the source. |
| 9 | Stale result overwriting a later set? | **No** for metadata (keyed by channel, never removes). **Yes** for destinations, in the form of a dropped read — defect B. |
| 10 | Failures and retries? | §6. |
| 11 | Does refresh work via a full sweep? | **No.** Same call, luckier ordering. §2. |
| 12 | Debounce/throttle/MV3 timing? | The 1s coalesce is what defect B interacted with. Background-tab throttling can stretch the 45s rescue, which is why it sometimes looked like "never". |

## 6. Retry behaviour

**Unchanged, and deliberately so.** A failed metadata fetch writes nothing and
clears nothing:

- the stale record (if any) keeps being shown until `liveStateOf` ages it to
  `unknown` on its own — failure degrades toward "we do not know", never toward
  a wrong answer;
- `inFlight` is cleared in `finally`, so the channel is eligible again
  immediately;
- the next `want()` re-requests it, because `needsRefresh` is still true.

There is **no retry timer, and none was added** — a failing backend must not
become a request storm. What the fix changes is that there are now *more, and
more relevant, triggers*: a destination change is one, alongside tab activity,
social-graph changes, friend heartbeats and the 30-minute alarm. A transient
failure is retried on the next of those rather than on a dedicated timer.

Verified by test: a failed request leaves the cache empty, and the next trigger
requests it again and succeeds.

## 7. Root cause

> **A changed destination set was broadcast to the panel but never announced to
> the metadata service, so the panel drew channels nobody had asked Twitch
> about. The only thing that eventually asked was an unrelated trigger — the
> friend's next presence heartbeat — which is why enrichment was late, partial,
> and appeared to be fixed by refreshing. A second defect compounded it: a
> destination read requested while another was in flight was discarded rather
> than queued.**

---

## 8. Fix

Event-driven, no polling, no new timer.

### The missing trigger

```ts
const friendDestinationsStore = createFriendDestinations({
  fetch: () => listFriendDestinations(supabase),
  onChange: () => {
    wantMetadata()   // ← THE FIX
    broadcast()
  },
  onError: logError,
})
```

Enrichment first, then the broadcast. `want()` is synchronous and only *starts*
requests, so this costs nothing and keeps the two consequences of one event in
one place.

### The dropped read

`createFriendDestinations` remembers a request that arrives during a read and
re-runs once, instead of returning:

```ts
if (inFlight) { again = true; return }
...
.finally(() => { inFlight = false; if (again) { again = false; run() } })
```

### The smallest extraction necessary

`src/background/friendDestinations.ts` — the destination set, its coalescing,
its single-flight, and the one event "the set is now different". Roughly 80
lines of logic moved out of `index.ts` with its dependencies injected.

This was done because **the defect was again trapped in the one file that
cannot be imported**, exactly as the previous audit predicted. It is the
narrowest useful cut: the store owns the set and the notification, and
`index.ts` keeps the wiring. Nothing else was extracted, and the upcoming
testing-harness milestone now has a worked example of the pattern.

Also: `KickbackState.friendDestinations` is now typed `DestinationsByUser`
rather than `Record<string, string[]>`, so the read-only shape the store hands
out survives the boundary instead of being widened back to mutable.

### Deliberately not done

No polling. No metadata retry timer. No change to the 1s coalesce, the 2-minute
metadata TTL, or the 30-minute alarm. No change to `gravityModel`, thresholds,
the cap, or any presentation.

## 9. Tests that reproduce the failure

**`tests/extension/destinationsConvergence.test.tsx` — 23 tests.**

Composes the real pieces the worker composes — `createFriendDestinations`,
`createMetadataService`, `gravityChannels`, `KickbackPanel` — and drives them
with fake timers and deferred responses. Only the network and the clock are
faked.

| Group | Tests | Covers |
| --- | --- | --- |
| grows one to three | 4 | requests the two it lacks; does **not** re-request the fresh one; converges with no further destination change; broadcasts when metadata lands |
| **the wiring this replaced** | 4 | **never asks about the new channels**; **stays bare for a full minute**; recovers only when something unrelated fires; converges immediately with the shipped wiring |
| ordering and failure | 6 | second-before-third; third-before-second; all together; **no duplicate request for a channel already in flight**; failure then retry; destination removed mid-flight |
| the store's lifecycle | 5 | `onChange` only on a real change; coalescing; **does not drop a change that arrives during a read**; error without changing the set; `clear()` |
| reaches the screen | 1 | two bare cards → three enriched, with `>teamliquid<` becoming `TeamLiquid` |
| harness pin | 3 | the worker asks for metadata on change; derives enrichment from the store; no stray module-level copy of the set |

### How the failure is reproduced

The harness takes a `wiring` option. `broadcast-only` is the pre-fix behaviour,
and the four tests in **"the wiring this replaced"** assert it fails:

```
never asks about the new channels             → requested never contains teamliquid
leaves the panel drawing bare cards            → still bare after 60s, nothing in flight
recovers only when something unrelated fires   → converges only after a manual wantMetadata()
converges immediately with the wiring that ships → same scenario, enriched
```

That is the owner's symptom, in a deterministic test, both broken and fixed.

**Additionally**, removing the `wantMetadata()` call from `index.ts` and
re-running fails the harness pin *"asks for metadata when the destination set
changes"* — so the shipped wiring is bound to the tested wiring.

### The diagnostic, extended and proven present

`kickbackGravity.now()` gains a per-channel **lifecycle state** and two
counters:

```js
enrichment: {
  lirik:        { state: "cached",    enriched: true,  lastUpdated: "…", displayName: "LIRIK", live: "live", game: "…", viewers: 12400 },
  teamliquid:   { state: "requested", enriched: false, lastUpdated: null, … },
  timthetatman: { state: "missing",   enriched: false, lastUpdated: null, … }

destinationsPending: false
```

- `cached` — held and fresh
- `stale` — held; the next `want()` refetches
- `requested` — a fetch is open right now
- **`missing`** — on the map and **nobody has asked**. That is the bug state,
  and after this fix it should never be seen on a rendered destination.

## 12. Two-step manual retest

1. **Replace the build on the observing account** (sha256 `17e9a0f1…`), reload
   at `chrome://extensions`, refresh the Twitch tab. **Do not refresh again
   after this point** — refreshing is what used to hide the bug.
2. **With the observing panel already open and untouched, have the publishing
   account open a second and then a third stream.** Each new card must arrive
   **already enriched** — Twitch capitalisation, LIVE badge, category, viewers,
   avatar — within a second or two of appearing. No blank phase that later
   fills in, and no refresh needed.

*If a card stays bare*, run `kickbackGravity.now()` in that account's
service-worker console and read `enrichment`: `missing` means nothing asked
(this bug), `requested` means a fetch is open (just slow), `cached` with a bare
card means something else entirely.

## 14. Implications for the testing-harness milestone

This is the second consecutive defect that lived in `src/background/index.ts`,
and the second time the fix required extracting code before it could be tested.
That is now the clearest signal in the repository.

- **The extraction pattern works and should be the milestone's backbone.**
  `friendDestinations.ts` took ~80 lines and turned an untestable lifecycle into
  23 deterministic tests, including four that reproduce the original failure.
  The same treatment is owed to `wantMetadata`, `pushActivity`, `sessionChannel`
  and the broadcast assembly.
- **Async lifecycle is where the bugs are, not rendering.** Every browser defect
  this week — port reconnect, destination collapse, enrichment set, and this —
  was about *when* something ran, not *what* it computed. Harness design should
  prioritise fake timers and deferred responses over DOM assertions.
- **Deferred-promise harnesses beat mocks.** Being able to resolve responses out
  of order, fail one, and drain the rest is what made the ordering questions
  answerable. Worth generalising into a shared test utility.
- **A "nothing asked" state is worth surfacing everywhere.** `state: "missing"`
  makes a whole class of bug visible in one word. Any future cache should report
  the same distinction.
- **Real Chromium is still only needed for** eviction timing, shadow DOM,
  drag/resize, OAuth, cross-tab storage and chat scroll anchoring. Nothing in
  this investigation required a browser once the module was importable.
