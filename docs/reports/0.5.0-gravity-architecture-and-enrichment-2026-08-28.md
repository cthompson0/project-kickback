## 1. Executive conclusion

**The suspicion was correct, and it was narrower than feared.**

Multi-destination was **not** implemented as a parallel simplified pipeline.
Clustering, ranking, JOIN and card rendering were always shared — there has only
ever been one `clusterMembers`, one `socialGravity`, one `DestinationCard`. The
new cards are the *same* cards.

What **was** duplicated is the answer to one question: **"which destinations are
on the map?"** That question had **three independent implementations**, and
multi-destination was extended into two of them:

| # | Where | Derived from | Migrated to multi-destination? |
| --- | --- | --- | --- |
| 1 | `SocialGravity` (UI) | friends + destinations | ✅ last commit |
| 2 | `KickbackPanel` (analytics) | friends + destinations | ✅ from the start |
| 3 | **`wantMetadata()` (worker enrichment)** | **`presence.channel` alone** | ❌ **never** |

Number 3 is the regression. The worker asked Twitch about the friend's **legacy
primary channel only**, so of three destinations exactly one got a display name,
live badge, category, viewer count, title and avatar. The other two rendered as
raw lowercase logins with nothing on them — **"materially less complete"**,
exactly as reported, and "inconsistent" because the primary looked right.

**The cards were never simplified. They were unenriched.** No card code was
duplicated, and none needed changing.

**What was done:** one canonical `gravityModel()` now serves all three
consumers, and the enrichment set is derived from the same expansion the map is
built from, so it cannot fall behind again. The type at that boundary now
**requires** metadata, because omitting it was silent and total.

Classification: **one STRUCTURAL SMELL (now fixed), two LOCAL SMELLS (now
fixed), the rest HEALTHY.** No large refactor was needed and none was done.

## 2. Original singular Gravity pipeline

```
public.presence
  → list_friends()                          → Friend[] (presence.channel: string | null)
  → worker friendsState.friends
  → stampFriends(friends, presenceIndex)     → Friend[] with one Presence each
  → broadcast currentState()                 → KickbackState.friends
  → KickbackPanel                            → const { friends } = view
  → SocialGravity
      → friends.map(→ MemberLike<Friend>)
      → socialGravity(members, localActivity, undefined, selfId, metadata)
          → clusterMembers(...)              → MemberCluster<Friend>[]  (bucket by channel)
          → + liveStateOf(metadata[channel]) → GravitySection<Friend>[] (live, rank, canJoin)
  → DestinationCard per here/destination section
      → channelName(section.channel)         ← ChannelNameProvider ← metadata.displayName
      → meta = metadata[section.channel]     → gameName, viewerCount, title, profileImageUrl
```

Types along the way: `Friend`, `Presence`, `Activity`, `MemberLike<Friend>`,
`MemberCluster<Friend>`, `GravitySection<Friend>`, `ChannelMetadata`.

Enrichment is joined **once**, inside `socialGravity` (for `live`) and **once**
in the card (for everything else), both keyed by `section.channel`.

## 3. Multi-destination Gravity pipeline

Identical from `clusterMembers` onward. The only difference is upstream:

```
public.presence_destinations
  → list_friend_destinations()               → rows (user_id, channel, opened_at, last_active_at)
  → listFriendDestinations()                 → Record<user_id, string[]>
  → worker friendDestinations
  → broadcast                                → KickbackState.friendDestinations
  → KickbackPanel → SocialGravity
      → expandDestinations(members, destinations)  → one MemberLike PER DESTINATION
      → …then exactly the pipeline in §2, unchanged
```

**`newSimplifiedGravity(rawChannel)` does not exist.** The expansion produces
`MemberLike<Friend>` — the same type singular Gravity produces — carrying the
same `Presence` with a different `activity.channel`. Everything downstream is
literally the same code path. That was verified, not assumed: `socialGravity`
has exactly three call sites in `src/`, and all three now go through
`gravityModel`.

## 4. Analytics pipeline

```
KickbackPanel gravityMap  (= the canonical model)
  → gravityOpportunities(gravityMap)         → sections with channel + rank
  → { channel, rank, count, live, key: opportunityKey(...) }
  → client.reportExposure({ friends, gatherings, gravity })
  → worker analytics.noteExposure
```

**Before this change** it was a *sibling* derivation of the same shape — the
panel built its own map for analytics while the component built one for the
screen. That is how "analytics reported three impressions, the screen showed
one" happened. **After**, it is a **projection**: `gravityOpportunities` filters
the canonical model. There is no second derivation to disagree with.

## 7. Type-safety weaknesses found

### The one that mattered — and it is exactly what shipped

```ts
socialGravity(friends, localActivity, now?, selfId?, metadata?)
```

Five positional parameters, with **`metadata` last and optional**. Omitting it
compiles, runs, and produces a complete-looking map in which **every card has
lost its Twitch casing, live badge, category, viewer count and avatar**. The
failure is silent, total and invisible to a reader — a raw lowercase login is
indistinguishable from "the cache is cold".

That is precisely the shape the brief asked about: *"optional properties that
allow an unenriched destination to masquerade as enriched"*.

**Fixed by the canonical entry point:**

```ts
export interface GravityModelInput<T> {
  friends: readonly MemberLike<T>[]
  destinations: DestinationsByUser
  localActivity: Activity
  selfId: string | null
  metadata: Readonly<Record<string, ChannelMetadata>>   // REQUIRED
  now?: number
}
export function gravityModel<T>(input: GravityModelInput<T>): Array<GravitySection<T>>
```

A named object (no positional slips) with **required** `metadata`. Passing `{}`
is still legal — a cold cache is a real state — but it must be said out loud
rather than fallen into. **Compile-time, not test-time.**

### Also introduced

`DestinationsByUser` — a named type for `Readonly<Record<string, readonly
string[]>>`, which was being spelled three slightly different ways at three
boundaries.

### Considered and deliberately NOT introduced

`RawDestination` / `AuthorizedDestination` / `EnrichedDestination` as distinct
nominal types. **Rejected**, because they would not have prevented this bug and
would cost real complexity:

- A channel identity genuinely *is* a lowercase login string at every layer;
  branding it would add casts at each boundary without adding information.
- "Enriched" is not a property of a destination, it is a property of the
  **cache at a moment in time** — a channel can be enriched now and stale in
  thirty seconds. A type cannot carry that; `liveStateOf`'s freshness rule
  already does, correctly.
- The real boundary was *"did the caller supply metadata at all"*, and that is
  now a required field. That is the distinction which genuinely protects an
  architectural boundary; the other three would be mechanical.

The brief warned against creating all of them mechanically. One was worth it.

## 9. Exact enrichment regression root cause

`src/background/index.ts`, `wantMetadata()`, as it stood:

```ts
function wantMetadata(): void {
  const channels = friendsState.friends.flatMap((friend) => {
    const activity = friend.presence?.activity
    return activity?.type === 'watching' ? [activity.channel] : []
  })
  const here = currentChannel()
  if (here) channels.push(here)
  metadata.want(channels)
}
```

`friend.presence.activity.channel` is the **legacy singular primary** —
position one of the published set, maintained by `report_destinations` for
v0.4.1 compatibility. For Friend A at `lirik`, `teamliquid`, `timthetatman`
this asks Twitch about **`lirik` only**.

The consequence, exactly:

| Field | Source | `lirik` | the other two |
| --- | --- | --- | --- |
| Display casing | `metadata.displayName` via `ChannelNameProvider` | `LIRIK` | falls through to the raw login → **`teamliquid`** |
| Live badge | `section.live` ← `liveStateOf(metadata[c])` | `LIVE` | `unknown` → **no badge, and the whole stream row is suppressed** |
| Category | `meta.gameName` | shown | **absent** |
| Viewer count | `meta.viewerCount` | shown | **absent** |
| Title | `meta.title` | shown | **absent** |
| Avatar | `meta.profileImageUrl` | Twitch image | **letter placeholder** |
| JOIN | `section.channel` | works | **works** (identity, not enrichment) |

Note the amplification: `live === 'unknown'` suppresses the **entire**
`kb-gravity-stream` row by design — *"`unknown` earns SILENCE… so a cold cache
produces exactly the card this panel drew before metadata existed"*. That rule
is correct, and it is why two missing records removed category, live state and
viewers all at once, making the cards look structurally simpler rather than
merely unlabelled.

**Why no test caught it:** every panel-level test supplies `channelMetadata`
directly as state. The bug is in *what the worker asks Twitch for*, one layer
upstream of anything the panel can observe.

## 10. Architecture changes made

Four, all consolidating:

1. **`gravityModel(input)`** — `src/core/socialGravity.ts`. The single canonical
   Gravity model: expansion → clustering → metadata → ranking. Named-object
   input with **required** `metadata`.
2. **`gravityChannels(friends, destinations)`** — the channels the map will
   name, derived from the same `expandDestinations`. This is what enrichment is
   requested for.
3. **`DestinationsByUser`** — one named type for the read-side destination map.
4. **All three consumers routed through the canonical model:**
   - `SocialGravity` — names its inputs, renders the returned sections.
   - `KickbackPanel` — one `gravityMap`; the exposure report is
     `gravityOpportunities(gravityMap)`, a projection.
   - `kickbackGravity.now()` — calls `gravityModel`, so the diagnostic cannot
     describe a map the UI does not draw.

**Deliberately not done:** no state-management change, no backend change, no
component prop-contract rewrite, no new framework. `clusterMembers`,
`socialGravity`, `DestinationCard`, `JoinButton` and `ChannelNameProvider` are
untouched.

## 11. Canonical Gravity ownership after the change

> **`gravityModel()` in `src/core/socialGravity.ts` owns what Social Gravity
> contains. Every consumer calls it; nobody rebuilds it.**

| Consumer | How it consumes | May it re-derive? |
| --- | --- | --- |
| `SocialGravity` (screen) | `gravityModel(...)` → renders sections | No |
| `KickbackPanel` (analytics) | `gravityModel(...)` → `gravityOpportunities(...)` | No — projection only |
| `wantMetadata()` (enrichment) | `gravityChannels(...)` — same expansion | No |
| `kickbackGravity.now()` (diagnostic) | `gravityModel(...)` | No |

**The encoded invariant:** *a destination is on the map, is enriched, and is
reported to analytics, or none of the three.* Asserted by test in §13.

`socialGravity()` remains exported and unchanged — `gravityModel` is a thin
canonical wrapper over it, so the selector's own tests keep testing the
selector.

## 12. Current regression fix

`wantMetadata()` now asks for exactly what the map will show:

```ts
const channels = gravityChannels(
  stampFriends(friendsState.friends, presenceIndex).map((friend) => ({
    member: friend, presence: friend.presence, userId: friend.user.id,
  })),
  friendDestinations,
)
const here = currentChannel()
if (here) channels.push(here)
metadata.want(channels)
```

Two details that matter:

- **`stampFriends`** — `friendsState.friends` carries presence only as last
  broadcast; stamping applies the live presence index, the same value the panel
  renders from. Without it a freshly-arrived friend could be asked about a beat
  late.
- **`metadata.want` is idempotent** and fetches only what is missing or expired,
  so widening the set from one channel to three costs one request the first
  time and nothing afterwards. No new request rate, no new cache.

**No enrichment was duplicated.** The multi-destination cards now go through the
same fetch, the same cache, the same `ChannelMetadata`, the same
`ChannelNameProvider` and the same `DestinationCard` as the singular ones — and
§13 proves the primary card is now byte-identical with and without destination
data.

## 17. Recommendations for the frontend/browser testing milestone

Concrete, from what this investigation actually hit. **Not started here.**

### Boundaries that are poorly tested today

| Boundary | Why it is exposed |
| --- | --- |
| **The service worker's own logic** | `src/background/index.ts` cannot be imported (chrome globals at module scope), so `wantMetadata`, `pushActivity`, `sessionChannel` and the analytics wiring are guarded only by **source-pin string matching**. Three of them broke on a line-ending change this session. **This is the single highest-value fix**: extract the worker's decision functions into importable modules taking explicit state, leaving `index.ts` as wiring. Both regressions this week lived in exactly that untestable zone. |
| **Worker → panel state contract** | `currentState()` is asserted field-by-field nowhere; a field silently missing from the broadcast is invisible until a browser test. |
| **Metadata request set** | Now guarded by one seam assertion (§13). Should be a behavioural test once the worker is importable. |
| **MV3 port lifecycle** | Covered now (`workerPortPublishing.test.ts`) but with a hand-written fake `chrome.runtime`. Fine, and worth keeping — real Chromium is not needed for it. |

### Behaviours that genuinely require real Chromium

- **Service-worker eviction and revival**, including background-tab timer
  throttling. Simulated today; the real timings are not reproducible.
- **Shadow DOM rendering and CSS isolation** — the panel lives in a shadow root
  over Twitch's own DOM.
- **Drag, resize and layout persistence** across reloads.
- **`chrome.identity.launchWebAuthFlow`** sign-in.
- **Cross-tab storage sync** (`chrome.storage` + the `storage` event).
- **Scroll anchoring in chat** — jsdom needed a hand-built geometry harness; a
  real layout engine would make those tests honest.

### Flows that want panel-level tests (cheap, no browser)

Panel-level SSR tests caught both of this week's UI regressions, and they are
milliseconds each. Extend to: Groups roster and group chat, the user card,
JOIN attribution, the session/Stream Room tab, empty and error states, the
sign-in states, and the notification/attention surface.

### Friends-beta regressions that deserve permanent E2E coverage

1. Multi-destination publishing across 3 tabs (write → hosted rows).
2. Observer sees a friend at every destination, **enriched** (this report).
3. Chat autoscroll and the "New messages" affordance.
4. Stream Room resolution on arrival — the bug that returned an empty cached room.
5. Panel layout persistence across tabs and reloads.

### What should stay manual

- Twitch DOM changes breaking the anchor or chat-rail measurement — an external
  dependency that changes without notice; a failing E2E here would be noise.
- Real Twitch OAuth against a live account.
- Visual polish, spacing and motion judgement.
- Desktop notification appearance and OS behaviour.

### Suggested shape

Playwright with a persistent context and the unpacked extension, one seeded test
account pair, and hosted Supabase pointed at a **test analytics environment**.
Keep it to ~6–10 high-value journeys; the panel-level SSR tests should stay the
bulk of the coverage because they are 1000× cheaper and caught the real bugs.
