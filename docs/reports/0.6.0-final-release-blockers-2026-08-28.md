## 5. Badge projection architecture

**`0027_badge_projection.sql` — one function, one fact.**

```sql
create or replace function public.list_displayed_badges()
returns table (user_id uuid, badge_key text, name text, icon text, issuer text)
language sql stable security definer
```

Style follows the project's established convention — the same shape
`list_friend_destinations()` uses: `SECURITY DEFINER`, seeded at
`public.require_actor()`, **no user parameter**, returning every visible row
rather than answering per-person queries.

**Why not widen `user_preferences`.** That table also holds presence visibility
and notification settings. A policy broad enough to expose
`displayed_badge_key` to friends would expose *"hide my activity"* too —
precisely the kind of quiet privacy regression nobody notices from outside. The
column is not the unit of authorization here; the fact is. **`user_preferences`
remains self-only, and a test asserts it.**

**Ownership is re-proved on read.** The join to `user_badges` *is* the check, so
a preference naming a badge the person does not hold produces no row — even if
it were set behind the RPC's back. Tested by writing the preference directly as
the table owner and asserting the projection stays empty.

## 6. Badge authorization and privacy

**Self, an accepted friend, or a shared group** — the identical predicate list
that gates presence, destinations and badge ownership. Badges are social
identity, so they travel with the social boundary rather than getting one of
their own that could drift.

`is_friend` and `shares_group_with` already carry the block check **in both
directions** (0022), so blocks are inherited rather than restated — blocking
somebody removes their badge for the same reason it removes their presence.

**Not a directory.** No user parameter exists; a caller cannot ask about an
arbitrary account or enumerate anyone.

**Returned:** `user_id`, `badge_key`, `name`, `icon`, `issuer` — five fields, and
a test pins that list exactly.

**Not returned:** every other preference column, presence visibility,
notification settings, invite codes, referral counts, award timestamps, award
reasons, and **badges the person owns but did not choose to display**.

**No badge selected → no row.** Established convention: absence rather than a
null sentinel.
