# KICKBACK — v0.5.0 GRAVITY MULTI-DESTINATION FAILURE

**Date:** 2026-08-28
**Type:** defect investigation and fix
**Starting HEAD:** `75dcac6` — `docs: record the browser publisher fix commit and push`
**Version:** 0.5.0, unchanged
**Hosted analytics schema version:** **25** — unchanged, **no migration required**

**Classification: implementation defect.** Not a threshold behaviour, not a
product-design gap, not a compatibility collapse. **No product decision is
needed.**

No SQL was written or applied. No migration. No server read behaviour, no
Friends redesign, no `+2 streams` affordance, no change to the 3-destination
cap, and **no change to any Gravity threshold**.

---

## 1. Expected product invariant

From the approved 0025 architecture:

- a user may publish up to **3** active destinations;
- **Social Gravity consumes EVERY authorized active destination**;
- a friend therefore contributes presence to several Twitch destinations at once;
- the Friends UI may stay singular/primary for compatibility;
- **Gravity is the multi-destination consumer.**

So with Friend A holding `lirik`, `teamliquid`, `timthetatman`, the observing
account's Gravity data model must receive Friend A at all three, and the read
path **must not** collapse them to `legacy_primary`.

---

## 2. Observed browser behaviour

- Write side: **PASS.** Worker logged `report_destinations Array(3)`; hosted
  `presence_destinations` held three active rows; the cap behaved as designed.
- Read side: **FAIL.** On another v0.5.0 account, Social Gravity showed the
  friend at one destination only — effectively singular presence.

**Reproduced exactly, as a test, before anything was changed.** Rendering the
real panel with `friends: [FriendA]` and

`teamliquid` and `timthetatman` appear nowhere in the document. That is the

## 3. Database and read result

**Correct at every boundary.** Nothing here was changed.

| Boundary | Rows / shape | Verdict |
| --- | --- | --- |
| `public.presence_destinations` | 3 rows for Friend A | ✅ owner-confirmed |
| `list_friend_destinations()` | one row per `(user_id, channel)` — 3 rows. No aggregation, no `distinct on` | ✅ covered by `tests/db/presenceDestinations.test.ts` and `destinationCollapse.test.ts` |
| `listFriendDestinations()` (`supabaseBackend.ts:454`) | accumulates with `list.push(entry.channel)` into `Record<user_id, string[]>` | ✅ appends, never assigns |
| worker `friendDestinations` (`index.ts:663`) | `{ a: ['lirik','teamliquid','timthetatman'] }` | ✅ |
| broadcast `currentState()` (`index.ts:1329`) | `friendDestinations: { ...friendDestinations }` | ✅ plain record of arrays, JSON-safe |
| panel `view.friendDestinations` | same object | ✅ |

Answering the specific questions asked:

- **Any Map/Record keyed by `user_id` that overwrites?** No. The value is a
  `string[]` and it is appended to.
- **Any dedupe assuming one channel per friend?** No. The only de-duplication is
  *within* one friend's channel list.
- **Any compatibility shim collapsing to legacy primary?** No — and this is worth
  being precise about. `presence.channel` (the legacy primary) is carried on
  `Friend.presence` and is deliberately kept singular. It never overwrites
  `friendDestinations`; the two are separate top-level fields specifically so
  one cannot shadow the other.
- **Does Gravity query the destination RPC in the real bootstrap?** Yes.
  `refreshFriendDestinations()` runs on sign-in (`index.ts:1834`), on realtime
  resync, coalesced one second after any friend presence change, and on the
  half-hourly alarm.

## 6. Gravity aggregation result

`gravityMap` was used in exactly one place (`KickbackPanel.tsx:476`):

```ts
gravity: arm === 'gravity' ? gravityOpportunities(gravityMap).map(…) : …
```

— the **analytics exposure report**. It was never rendered.

The rendered component was handed the plain, singular friends list:

```tsx
<SocialGravity friends={friends} localActivity={view.localActivity} … />
```

and clustered it itself (`SocialGravity.tsx:461`), one entry per friend:

```ts
socialGravity(
  friends.map((friend) => ({ member: friend, presence: friend.presence, userId: friend.user.id })),
  localActivity, undefined, cardContext.selfId, metadata,
)
```

One friend, one presence, one channel — `presence.channel`, the legacy primary.
**One card.**

The irony is on the record in the source: the comment above `gravityMap` reads
*"The same map the Friends tab draws, for the exposure report. Derived from the
same selector rather than re-clustered, so what analytics calls an impression is
exactly what was on screen. Recomputing it a second way would be a second chance
to disagree."* It was recomputed a second way, and the two disagreed. Analytics
was recording three impressions for a screen showing one.

## 7. Exact qualification / threshold rule

Stated precisely from code, because the brief asks for a definitive answer.

**There is no minimum. Every channel with at least one visible friend becomes a
section, and every such section renders as a card.**

- `clusterMembers` (`src/core/groupPresence.ts:97-135`) buckets every member by
  channel and emits a cluster for each. No size filter anywhere.
- `socialGravity` maps each cluster to a section and ranks every one whose
  `canJoin` is true. No size filter.
- `SocialGravity` renders a `DestinationCard` for every `here` and `destination`
  section. No size filter.
- `GRAVITY_THRESHOLD = 2` and `isGravity()` control **emphasis only** — the
  gathering flame and the heavier card treatment. The source says so:
  *"ONE FRIEND IS STILL A DESTINATION. A single friend on a stream is real
  social discovery, so it gets a row of its own rather than being hidden until a
  second person turns up. What changes with size is emphasis, not existence."*

**So the answer to the brief's critical distinction is unambiguous:**

> **(A) — destinations were being lost before they reached the screen.**
> **NOT (B).** The threshold suppresses nothing. Had the expansion been wired
> through, all three destinations would have rendered as three cards, each
> reading "1 friend", from the moment the data arrived.

Asserted directly (`gravityMultiDestination.test.tsx`): three destinations →
three `destination` sections, each `count: 1`, all three `canJoin`, ranked 1, 2,
3.

---

## 8. Root cause

> **The multi-destination expansion was wired to the analytics exposure report
> instead of to the rendered component. `KickbackPanel` computed the correct
> three-destination map for analytics and, beside it, rendered
> `<SocialGravity friends={friends} />` — a component that clustered the plain
> singular friends list on its own and had no way to know destinations existed.
> Both halves were individually correct; nothing joined them.**

The defect is a single missing prop, and it survived because the expansion had
two homes: the panel's (correct, unrendered) and the component's implicit one
(singular, rendered).

### My earlier report was wrong about this, and it is worth saying why

`docs/reports/0.5.0-multi-destination-smoke-failure-2026-08-28.md` §3 lists
layer 11, "Social Gravity expansion — `KickbackPanel.tsx:392`", as **correct**.
That assessment was true of the expansion and false as a claim about the
product: I verified the map was computed and clustered correctly, and never
checked **which map the rendered component consumes**. Tracing a value forward
until it looks right is not the same as tracing it to the screen.

---

## 9. Implementation defect vs product-design gap

**Implementation defect. Unambiguously.**

The invariant is explicit in the approved architecture — "Gravity is the
multi-destination consumer" — and the implementation intended it: the expansion
exists, is documented, is tested, and is computed on every render. It simply was
not connected to the component that draws.

- **Not a threshold behaviour.** §7: the threshold suppresses nothing.
- **Not a compatibility collapse.** The legacy singular fields behaved exactly
  as designed and never overwrote anything.
- **Not a UX hole.** The product already has a visible way to show one friend at
  several destinations: one card per destination, each naming the friend. That
  is precisely what now renders.

Because the invariant is unambiguous and the defect is a missing wire, it was
fixed narrowly, as instructed. **No product decision is required, no threshold
was touched, and no new UI concept was invented.**

## 10. Fix

### One expansion, in one place — `src/core/socialGravity.ts`

`expandDestinations(friends, destinations)` is now exported from core, with the
panel's logic moved into it verbatim: one entry per friend per active
destination, defensively de-duplicated, falling through unchanged for a friend
with no destination rows or a non-watching presence.

It lives in core rather than in either consumer **because having it in two
places is what caused this**. Its doc comment records that.

### The rendered component consumes it — `src/ui/components/SocialGravity.tsx`

A new **optional** `destinations` prop, defaulted to a stable empty record, fed
through `expandDestinations` inside the component's existing `useMemo`:

```ts
socialGravity(
  expandDestinations(friends.map((friend) => ({ … })), destinations),
  localActivity, undefined, cardContext.selfId, metadata,
)
```

Optional and defaulted on purpose: **omitting it produces exactly the map this
component produced before multi-destination existed**, so every existing render
test still asserts what it always asserted, and a friend with no destination
rows — a v0.4.1 client, or anyone before the first read lands — still appears at
their single presence channel.

### The panel passes it — `src/ui/KickbackPanel.tsx`

```tsx
<SocialGravity friends={friends} destinations={view.friendDestinations} … />
```

and `gravityMap` now calls the same shared `expandDestinations`, so the analytics
map and the rendered map cannot drift apart again.

### What was deliberately not done

No threshold change. No Friends redesign. No `+2 streams` badge. No change to the
cap. No change to `clusterMembers`, so HERE, group rosters, the user card and
JOIN eligibility still answer from one interpretation of presence.

### The observer diagnostic — `kickbackGravity.now()`

Behind the same build-time constant as the existing probes, in the **service
worker** console. It runs the **real** selector on the **real** state through
the **same** `expandDestinations` the panel uses, so it cannot report a map the
UI does not draw — which matters, because reporting a map the UI ignored is
precisely the defect being fixed.

```js
kickbackGravity.now()
```

```js
{
  signedIn: true,
  received:   { friend_a: ["lirik", "teamliquid", "timthetatman"] },
  friendsWithDestinations: 1,
  gravityInput: { lirik: ["friend_a"], teamliquid: ["friend_a"], timthetatman: ["friend_a"] },
  gravityInputCount: 3,
  gravityOutput: [
    { channel: "lirik",       kind: "destination", count: 1, rank: 1, rendered: true, gathering: false,
      why: "rendered as a destination card, without the gathering flame (1 friend)" },
    { channel: "teamliquid",  kind: "destination", count: 1, rank: 2, rendered: true, gathering: false, why: "…" },
    { channel: "timthetatman",kind: "destination", count: 1, rank: 3, rendered: true, gathering: false, why: "…" }
  ]
}
```

Friend usernames and channel names appear here. Development and beta only;
nothing reaches analytics or failure telemetry. No tokens, no emails, no message
bodies, no friend codes.

### Worth knowing before you look

A friend alone at three destinations produces **three cards each reading
"1 friend"**, without the gathering flame — that is correct and by design.
The flame appears at two or more people on one channel. If you want a second
opinion on whether that is the right *emphasis* for one person in three places,
that is a genuine product question, and it is separate from this defect. It was
deliberately not pre-empted here.
