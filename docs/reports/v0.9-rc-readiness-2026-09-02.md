## 2. The stop-ship: reporting views were readable by every client

**Supabase grants `SELECT` on anything newly created in `public` to `anon` and
`authenticated` by default.** Every earlier reporting view knows this and revokes
explicitly — the whole `analytics_*` set, the whole `m3d_*` set, `feedback_v`.

**Four migrations in a row did not:**

| Migration | Views left exposed |
| --- | --- |
| 0038 (M5C) | `acquisition_actor_v`, `acquisition_campaign_v`, `acquisition_downstream_v` |
| 0039 (M6B) | `ops_client_failures_v`, `ops_health_v` |
| 0040 (coverage) | `acquisition_coverage_v`, `acquisition_touch_outcomes_v` |
| 0042 (activation) | `activation_actor_v`, `activation_funnel_v` |

**Why it is serious rather than untidy.** A view runs with its *owner's*
privileges, so the careful `revoke all on public.users from anon, authenticated`
in 0002 does not protect a view built on top of it. These are **per-actor**
views: `acquisition_actor_v` carries every user's acquisition campaign,
first-touch time, JOIN clicks, arrivals, gravity impressions, observed dwell and
friend count. `activation_actor_v` carries when each account formed its first
friendship.

**And `anon` is not hypothetical** — the publishable key ships inside the
extension and is public by design, so these were reachable over PostgREST by
anybody who read the bundle.

**Proved, not reasoned about.** A signed-in role SELECTed `activation_actor_v`
successfully in the harness, which deliberately models Supabase's default grants
(*"Supabase hands anon/authenticated full DML on anything new in public"*, said
in the harness's own comment).

**Fixed by 0043** — revokes all nine views plus 0038's two immutability trigger
functions. **Two of the four offending migrations were mine**, from the previous
two milestones.

**The real fix is the test.** `tests/db/authorizationSurface.test.ts`
introspects the built schema and fails on *any* reporting view that is
client-readable. Review missed this four times; a check that asks the database
cannot.

## 5. Security findings

### Authentication and tokens — clean

- `provider_token` / `provider_refresh_token` appear in the bundle in exactly
  three places, all correct: supabase-js's own session destructuring, the O7
  **stripper** that removes them before anything is persisted, and the M3D
  capture path.
- The capture path holds the credential in memory, posts it to the Edge Function
  **in a body, not a URL**, logs a **fixed string** on failure — never the value
  or its length — and has **no retry loop**, deliberately, so a plaintext
  credential is not kept alive.
- No JWT, no `service_role`, no `client_secret`, no private key in either
  artifact.

### Database authorization — one defect (§2), rest clean

- **Every** SECURITY DEFINER function has a pinned `search_path`.
- **No client-callable function takes an actor id.** Three take `p_actor` —
  `apply_destinations`, `join_context_for_attribution`,
  `purge_creator_relationships` — and all three are revoked from `anon` and
  `authenticated`. My first version of this test matched on the parameter name
  and produced three false positives; it now checks the grant, which is what
  actually makes them safe.
- `purge_twitch_derived` and `analytics_emit_server` are callable by no client.
- **`anon` can execute nothing and read no table.**
- `twitch_credentials` grants nothing to either role and has RLS on.
- No table carrying user data has RLS off with a grant.

### Extension trust boundary — clean

- Port name checked; a closed `switch` on message type, so no arbitrary action
  dispatch; values type-checked at the boundary.
- **No `window.addEventListener('message')`** anywhere — a hostile Twitch page
  cannot inject messages into the extension.
- No `externally_connectable`, no `web_accessible_resources`.

### XSS — clean

**Watchside's own code contains zero `innerHTML`, zero
`dangerouslySetInnerHTML`, and no raw DOM injection.** Everything renders through
React's escaping. The five `innerHTML` and one `dangerouslySetInnerHTML`
occurrences in the bundle are React's own DOM internals — and the `javascript:`
match is React's *protection*, which blocks such URLs. Emote images already set
`referrerPolicy="no-referrer"`.

### Network / remote code — clean

No `eval`, no `new Function`, no `importScripts`, no WebAssembly, no remote
script tags, no dynamic script injection, no permissive CSP. Destinations match
the manifest and the privacy policy exactly: the Supabase backend, `7tv.io`,
`cdn.7tv.app` and `static-cdn.jtvnw.net` for images, `twitch.tv` for the panel.
The remote-code declarations remain truthful.

### Dependencies

**Production: 0 vulnerabilities.** Only `@supabase/supabase-js`, `react` and
`react-dom` ship.

3 high-severity findings exist in `web-ext` → `addons-linter` → `image-size` —
**devDependency only**, used to lint the Firefox package, present in no artifact.
**Classification: build-only, unreachable in shipped runtime. Not fixed**, per
the instruction not to upgrade on an audit number alone.

Every lockfile entry resolves to `registry.npmjs.org`.

### Logging — one backlog item

The only notable log is `[Watchside] presence write …`, which fires in shipped
builds and contains **the viewer's own channel names**, written to **their own
browser console**, transmitted nowhere. Not a leak of anyone else's data and no
tokens — but a public extension need not narrate itself. **NORMAL BACKLOG.**

No new data category appeared from Launch Activation, so the privacy policy and
both store disclosures remain accurate.
