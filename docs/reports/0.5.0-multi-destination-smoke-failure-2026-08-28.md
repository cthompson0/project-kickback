## 1. Observed manual failure

Reported by the owner from a real two-account browser test:

- Account A and Account B are Kickback friends.
- Account A runs the new local multi-destination build.
- Account A opens two different Twitch streams in two tabs.
- **Expected:** Account B observes A at both streams simultaneously; at three
  streams, all three, to a maximum of three.
- **Actual:** Account B observes A at exactly one stream.

The failure is real, it is reproducible in principle from the code, and it is
now reproduced by automated tests at two separate layers (§14). It was **not**
a hosted-schema problem, an authorization problem, a read-path problem or a UI
problem. Every one of those layers was correct.

## 2. Exact root cause

> **The fixed client published its presence twice, through two entry points
> that contradict each other, as two concurrent requests with no ordering
> between them. `report_presence` deletes every destination row that is not the
> single channel it names — which is exactly what it must do for a v0.4.1
> client — so whenever the singleton write landed second, every destination but
> one was deleted.**

Both writes were issued from `pushActivity()` in the same turn:

```ts
presenceReporter.setActivity(tabActivity.effective())    // -> report_presence(platform, channel)
presenceReporter.setDestinations(tabActivity.destinations())  // -> report_destinations(channels)
```

`createPresenceReporter` held **two independent debounced writers**, each with
its own timer, each firing `void write(...)`. Two HTTP requests went to
PostgREST at effectively the same moment. PostgREST executes them on separate
pooled connections. Nothing orders them.

There is also a **deterministic** variant that needs no race at all, described
in §6, and a **second, slower collapse** — a thirty-minute expiry with nothing
to refresh it — described in §6 as defect **B**. Both are fixed.

## 5. Exact point it collapsed to one

`src/background/presence.ts`, as of `5b9adb7`. Two writers, two timers:

```ts
let destinationTimer: ReturnType<typeof setTimeout> | undefined
let writeTimer: ReturnType<typeof setTimeout> | undefined
...
function flushDestinationsSoon(): void {
  clearTimeout(destinationTimer)
  destinationTimer = setTimeout(() => { ... void writeDestinations(desiredDestinations) }, debounceMs)
}
function flushSoon(): void {
  clearTimeout(writeTimer)
  writeTimer = setTimeout(() => { ... void write(desired) }, debounceMs)
}
```

`pushActivity()` calls `setActivity` then `setDestinations`, so `writeTimer` is
created first and fires first — but both callbacks only *start* an async RPC.
The two requests are then in flight together. The last one to reach Postgres
wins, and `report_presence` winning means one surviving row.

**It does not self-heal.** After the collapse the client believes
`reportedDestinations` is the full set, because `writeDestinations` succeeded.
`setDestinations` compares against that belief and returns early. The database
stays at one row until the destination set genuinely changes — at which point
the dice are rolled again. Asserted in
`tests/db/destinationCollapse.test.ts` → *"stays collapsed until the set
genuinely changes"*.

## 6. `report_destinations` / `report_presence` interaction

### The question, answered by execution

> If `report_destinations` writes `[A, B]` and `report_presence` subsequently
> writes `A`, what rows remain?

**Only `A`.** Proven against real PostgreSQL (PGlite, real migrations, real
`authenticated` role) in `tests/db/destinationCollapse.test.ts`:

```
leaves only the singleton when report_presence follows report_destinations   PASS
is visible to the friend as a single destination                             PASS
keeps whichever channel the singleton names, and only that one               PASS
erases every destination when the singleton names no channel                 PASS
```

The mechanism is in `0025`, and it is **correct**:

```sql
perform public.apply_destinations(
  v_actor,
  case when v_channel is null then '{}'::text[] else array[v_channel] end
);
```

and inside `apply_destinations`:

```sql
delete from public.presence_destinations d
 where d.user_id = p_actor
   and not (d.channel = any(v_clean));
```

A v0.4.1 client saying "I am on `shroud`" means *"`shroud` is the entirety of
where I am"*. Honouring that literally is the whole compatibility story, and it
is why the fix is on the client and not in SQL.

### And the new client was invoking both paths

Yes. Confirmed at `presence.ts` and `supabaseBackend.ts:418`. `write()` called
`reportPresence('twitch', channel)` for every non-idle activity, unconditionally,
alongside `writeDestinations`.

### The deterministic variant — no race needed

`effective()` prefers the **visible** tab; `destinations()` ignores visibility.
They can therefore disagree, and when they do the singleton wins outright:

- Tab 1 on `shroud`, tab 2 on `lirik`, tab 3 on `twitch.tv` itself.
- Focus tab 3. `effective()` → `browsing` (no channel). `destinations()` → still
  `['lirik','shroud']`, unchanged.
- `setDestinations` sees no change and writes **nothing**.
- `setActivity` writes `report_presence('twitch', null)` → `apply_destinations([])`
  → **every destination row deleted**, permanently, with no race involved.

Asserted: *"erases every destination when the singleton names no channel"*.

### Defect B — the slow collapse

Independent of A, and it would have passed a five-minute smoke and failed a real
session.

A destination is active for **thirty minutes** after `last_active_at`. **Nothing
refreshes it.** `public.heartbeat()` (`0006`) is:

```sql
update public.presence set last_seen_at = now()
 where user_id = v_actor and status = 'online';
```

`presence.last_seen_at` only. So a viewer who opens two streams and then simply
watches has both rows expire after half an hour. The account stays online, and
the legacy branch of `is_present_at` (`or p.channel = p_channel`) keeps them
visible on their primary channel alone — **the same collapse to one**, arriving
slowly. Asserted: *"collapses to the legacy primary once the rows age out"*.

### Defect C — focus was reaching the network

`destinations()` ordered by `updatedAt`, and `updatedAt` was re-stamped on every
report — including every `visibilitychange`. So switching between two open tabs
reordered the published set, changed the legacy primary channel other people can
see, and put a write on the wire. That is precisely the property the approved
architecture forbids.

### The heartbeat

Checked and cleared. It never wrote a singleton, and never touched destinations.

### Service-worker restart

Checked and cleared, before and after. Tabs reconnect their ports, the registry
rebuilds from all of them, and the whole set is republished — because the
reporter starts with nothing published, so the set is a change. Asserted:
*"rebuilds and republishes every live destination"*.

### One consequential change was needed here

`sessionChannel()` gated the room on `presenceReporter.lastReported()` — the
single activity of the last write. Under one-write-per-state that is wrong: a
viewer switching to a second open tab correctly writes nothing, so
`lastReported()` would never name that tab's channel and the tab would never
resolve its own room. It now asks the **published destination set**, which is
literally what the server holds and exactly what `is_present_at` consults:

```ts
return presenceReporter.lastDestinations().includes(here) ? here : null
```

This is stricter about the right thing and looser about the wrong thing.

## 11. Fix implemented

Three changes, all client-side, all in the service worker.

### A — one write per state (`src/background/presence.ts`)

The two debounced writers are replaced by **one**, which decides which single
call expresses the current state:

```
idle                      -> reportOffline()
any stream open           -> reportDestinations(the whole set)
on Twitch, nothing open   -> reportPresence('twitch', null)
```

The watching case never reaches `report_presence`. This is deliberately the
shape that **prevents** the race rather than the shape that sequences it: there
is no second write to order.

Supporting structure:

- A `Publication` union (`offline` | `destinations` | `presence`) records what
  the server was told, in the shape it was told it. Intent is compared against
  that, not against the pieces it was assembled from — `['a']` as a set and
  `'a'` as a singleton leave identical rows but are not the same call.
- `lastDestinations()` is derived from the publication, so it is always exactly
  what the server holds — including the one-element set a browsing/legacy write
  leaves behind.
- A `writing` guard: if a write is in flight, the next flush waits for it rather
  than going out beside it.
- Failure still does not retry. `publish()` resolves `false`, and nothing
  re-arms until a real change arrives.

### B — keep a published set from ageing out (same file)

On each heartbeat tick, if something is published and it has been
`destinationRefreshMs` (default **10 minutes**, a third of the thirty-minute
window) since the last publish, the set is stated again. Two refreshes may be
missed before anything expires. Cost: six writes an hour against a budget of
ninety a minute. The `destinations_published` analytics event fires only on a
genuine change, never on a refresh.

### C — focus stops reaching the network (`src/background/activity.ts`)

Each tab now carries `channelAt` — when it arrived at the channel it is on now —
carried forward across every later report that does not change the channel.
`destinations()` orders by that, and dates a destination by the **earliest** tab
still showing it. Consequences:

- A `visibilitychange` does not reorder the set, so no write goes out.
- A duplicate tab on an already-published stream changes nothing at all.
- Navigation and opening a new stream still reorder, because they are real.

### D — gate the room on what was published (`src/background/index.ts`)

`sessionChannel()`, as described in §9.

## 13. Max-3 semantics, made explicit

**Deterministic rule.** The published set is the **three most recently opened
destinations**, newest first, ties broken by channel name.

**How recency is updated — exhaustively:**

| Event | Effect on a destination's position |
| --- | --- |
| A tab first reports a channel | that channel is dated **now** |
| A tab navigates to a different channel | the new channel is dated now; the old one is dropped if no other tab shows it |
| A second tab opens on an **already published** stream | **nothing**. The destination keeps its original date. |
| A tab becomes visible or hidden | **nothing** |
| The page title settles, `pageshow` fires, the port reconnects | **nothing** |
| A duplicate tab closes while another remains | **nothing** |
| The last tab on a destination closes | the destination is dropped |

A destination is dated by the **earliest** tab still showing it — its opening —
which is the same idea `presence_destinations.opened_at` encodes.

**Opening a fourth stream D:** D is dated now, so it enters at position one. The
destination whose opening is oldest falls out. With A, B, C opened in that
order, D displaces A. Enforced twice: capped at three in `destinations()`, and
capped at three again in `apply_destinations` — the server is the boundary, the
client copy only avoids sending work that would be thrown away.

**"Most recently active" explicitly does not mean focus.** There is no
attention signal anywhere in this path, by design. Activity means *arrival at a
destination*: opening it or navigating to it. Looking at a tab is not activity,
does not reorder anything, and produces no network traffic. Three tests assert
this directly, including the strong form — a sequence of focus switches produces
**zero** writes.

`tests/db/destinationCollapse.test.ts`, so the table and column names are known
good rather than plausible.

Channel names are visible here because this is owner-operated development
diagnostics on your own test account. **None of this goes anywhere near
analytics or failure telemetry.**

Replace `'REPLACE_ME'` with the **Twitch login** of the publishing test account
(Account A). No user IDs needed.

### Query 1 — is the account live, and how many destinations does it have?

```sql
select ca.platform_login,
       p.status,
       p.channel                                     as legacy_primary,
       p.last_seen_at,
       now() - p.last_seen_at                        as liveness_age,
       (p.status = 'online' and p.last_seen_at > now() - interval '90 seconds')
         as parent_live,
       (select count(*) from public.presence_destinations d
         where d.user_id = ca.user_id)               as destinations_total,
       (select count(*) from public.presence_destinations d
         where d.user_id = ca.user_id
           and d.last_active_at > now() - interval '30 minutes')
         as destinations_active
  from public.connected_accounts ca
  left join public.presence p on p.user_id = ca.user_id
 where ca.platform = 'twitch'
   and ca.platform_login = lower('REPLACE_ME');
```

### Query 2 — what are they, and would a friend see them?

```sql
select d.channel,
       d.opened_at,
       d.last_active_at,
       now() - d.last_active_at                          as destination_age,
       d.last_active_at > now() - interval '30 minutes'  as destination_active,
       public.is_present_at(d.user_id, d.channel)        as visible_to_a_friend
  from public.connected_accounts ca
  join public.presence_destinations d on d.user_id = ca.user_id
 where ca.platform = 'twitch'
   and ca.platform_login = lower('REPLACE_ME')
 order by d.last_active_at desc, d.channel;
```

### How to read the answer

| What you see | What it means |
| --- | --- |
| `destinations_total` = 3 with three tabs open, all `destination_active`, all `visible_to_a_friend` | **The write path is working.** Any remaining problem is read or UI. |
| `destinations_total` = 1 with three tabs open | **Write failure** — the original bug, or a new one shaped like it. |
| `destinations_total` = 0 with tabs open | Either signed out, presence visibility set to invisible/hide-activity, or the write is failing outright. Check `status` in query 1. |
| Rows exist but `destination_active` is false | **Defect B** — the thirty-minute expiry, with the refresh not running. |
| `parent_live` is false | The account is stale — worker asleep or the heartbeat is failing. Destinations are correctly hidden. |
| `legacy_primary` is not the most recently opened stream | The publish order is wrong (defect C shape). |
| Everything above healthy, Account B still shows one | Read or UI. Check Account B's `list_friend_destinations()` next. |

## 18. Known limitations

1. **The version is 0.4.1, not 0.5.0.** §15. Owner decision; not silently fixed.
2. **`effective()` can name a channel outside the published three.** With four or
   more tabs, the visible tab may be the one the cap excluded. HERE and
   attribution would then point at a destination that is not published, so that
   tab shows no room. Requires four-plus simultaneous streams; not reached in the
   retest below. Not fixed here because it is a cap-policy question, not a
   collapse.
3. **The refresh is worker-lifetime.** If the service worker is evicted for more
   than thirty minutes with tabs still open, destinations expire until a tab
   event revives the worker. MV3 wakes the worker on port activity, so a live
   Twitch tab makes this unlikely; it is not proven impossible.
4. **The primary channel is the most recently opened, not the most recently
   watched.** Deliberate — the alternative requires an attention signal, which is
   forbidden. A v0.4.1 friend may therefore see you at a stream you opened last
   rather than the one you are looking at.
5. **Manual browser behaviour is still unverified.** Everything here is proven in
   PGlite and in a modelled worker. Two Chrome profiles against hosted Supabase
   is the only thing that closes it, which is §19.
6. **`test:authz` was not run**, as instructed. The 14/18 mutation-detection
   finding from the Patch 1 checkpoint stands unchanged and uninvestigated.
