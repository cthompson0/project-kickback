# v0.9 consolidated beta feedback + accessibility polish

**Date:** 2026-09-02
**Base:** `a5cf0fd` (G7 gate)
**Head:** see §76
**Scope:** eleven organic beta reports, a text-size accessibility setting, a
layout audit at every size, a basic accessibility pass, a fresh v0.9.0 RC, and
a bounded native-integration exploration.

Nothing was submitted to Chrome or Firefox. No migration was written. No
permission, host, scope or destination changed. G7 was not touched.

---

## The one thing worth reading first

Six of the eleven reports were the same kind of defect: **a surface telling the
truth about its own state, and a second surface disagreeing.** A local `added`
map that no server answer could clear. A wordmark painted from the token that
exists to be a *background*. A count badge borrowing the visual language of
unread items. A cursor that said "move" where the gesture meant "resize". In
each case the code was internally consistent and externally wrong, and the only
way to find that was to ask the running product rather than the source.

So most of what follows was **measured in a real browser** — Chrome through the
Test Lab and the repository's own CDP harness — and three of the fixes below
exist *only* because a measurement contradicted what the stylesheet said.

Two defects in this report were introduced by fixes earlier in this same pass
and caught by the same method. They are called out where they occur.

# Part 1 — the eleven reports

## Feedback 1 — a cancelled request would not go back to "Add"

> "add friend request, cancel it, have to leave page entirely to get the Add
> button back, small QOL the 'people you may know' could refresh on such
> actions"

**1. Root cause.** `FriendSuggestions` in `src/ui/components/GrowFriends.tsx`
held `const [added, setAdded] = useState<Record<string, string>>({})`. It was
written on Add and **never cleared by anything**. Its fetch effect had
dependencies `[client]`, so it ran once. "Requested" therefore survived until
the component unmounted — which is literally what "leave the page entirely"
does. The reporter's workaround was not a workaround; it was the only code path
that reset the state.

**2. Exact relationship surfaces affected.** Only the suggestion rows. The
search results in `FindFriends.tsx` were already correct — they carry a
`relationship` field from the server and patch it optimistically, then let the
backend's answer overwrite it. The Sent list was correct too, being rendered
straight from `outgoingRequests`. This was one component disagreeing with two
that were right.

**3. The reconciliation fix.** The map is gone. A row now derives its label from
authoritative worker state:

```tsx
function suggestionAction(userId, friends, outgoingRequests) {
  if (friends.some((f) => f.user.id === userId)) return { label: 'Friends', actionable: false }
  if (outgoingRequests.some((r) => r.user.id === userId)) return { label: 'Requested', actionable: false }
  return { label: 'Add', actionable: true }
}
```

`friends` and `outgoingRequests` are threaded `KickbackPanel → FindFriends →
FriendSuggestions`. No new fetch, no new state, no refresh call — the panel
already re-renders on every worker broadcast.

**4. Send/cancel/accept/reject/remove/block/unblock.** No change was needed
here, and that is worth stating rather than assuming: `mutate()` in
`src/background/friends.ts` already `await refresh()`s after **every** mutation
before its promise resolves, and `refresh()` broadcasts. So the worker was
always authoritative and always current; the suggestion list simply was not
reading it. Blocking still tears down the friendship and cancels any pending
request server-side in one transaction, and the re-read after it is what makes
the panel stop drawing somebody the graph no longer contains.

**5. Mutual Friend Suggestions reconciliation.** The existing feature was
reconciled, not replaced. No new discovery system, no new ranking, no new
queries. A cancel performed *anywhere* — the Sent list, a search result, another
Twitch tab — now shows up here, because all of them go through the same worker
state.

The regression is guarded twice: behaviourally, by a test that re-renders with
new props and asserts the row returns to ADD **without remounting**; and
structurally, by `expect(source).not.toMatch(/setAdded|const \[added/)`, because
the defect class is "a local record that can contradict the server".

## Feedback 2 — "@name" found nobody, and every name was printed twice

> "when i type @ in front of the name it doesnt find them"
> "find friends, peoples names are listed twice, wtfchuck27 then below that is
> @wtfchuck27, its not clear which is meant to go into the find friend text field"

**6. Root cause of the @ failure.** The query was passed through untouched, so
the database matched `@wtfchuck27` literally and found nothing. The UI taught
the syntax — it printed handles as `@login` — and then rejected it.

**7. Final normalisation rules.** One leading `@` is stripped, once, in
`src/core/twitchMetadata.ts`:

```ts
export function normalizeSearchQuery(raw: string): string {
  const trimmed = raw.trim()
  return trimmed.startsWith('@') ? trimmed.slice(1).trim() : trimmed
}
```

Applied in `friends.ts` `search()` **before** the minimum-length check, so
`"@"` alone never becomes a request at all. One leading `@` only: an interior
`@` is a real character and a second one is not a typo we should guess at.

**8. 0041 rate budget intact — confirmed.**
`consume_rate_budget('user_search', 60, interval '10 minutes')` in
`0041_search_rate_budget.sql` is unchanged and still inside the search RPC.
Normalisation is deliberately **client-side**, in the service worker, before the
call. Consequences, precisely:

- no migration is needed;
- the budget is charged exactly once per search, as before;
- `"@"` alone now returns `[]` without a request, which *reduces* consumption
  and can never increase it.

**9. Identity presentation root cause.** `display_name` and `login` are two
genuinely different Twitch fields, and for most people they differ only in
capitalisation. The row rendered both unconditionally, so it printed the same
word twice and left the reader to work out which was the identifier. The `@`
made it worse by teaching a syntax the lookup then rejected.

**10. Final identity presentation.** The handle is shown only when it says
something new:

```ts
function handleFor(displayName, twitchLogin) {
  if (!twitchLogin) return null
  if (twitchLogin.toLowerCase() === displayName.toLowerCase()) return null
  return `@${twitchLogin}`
}
```

"Chuck" over "@wtfchuck27" is informative. "wtfchuck27" over "@wtfchuck27" is
noise. A user with no Twitch login still gets a line ("Watchside user"), because
*that* absence is worth saying. The `@` stays where the handle is shown — it is
how Twitch handles are written everywhere else, and it now works. Applied to
both the search-result row and the outgoing-request row.

## Feedback 3 — Support was not centred

> "support ui/text isn't centred correctly"

**11. Root cause and fix.** Measured in Chrome against the real stylesheet, in a
320px panel:

| control | box | label centre vs box centre |
|---|---|---|
| Reset layout | 21…299 | **0.0px** |
| Feedback | 21…299 | **0.0px** |
| **Support** | 21…299 | **−104.0px** |
| Sign out | 21…299 | **0.0px** |

Support is the one anchor in a column of buttons. A `<button>` centres its own
label — that is the UA default — and an anchor does not. `a.kb-ghost-btn` makes
this one a flex container, at which point `text-align` stops reaching the label
entirely: the text becomes an anonymous flex item and sits wherever
`justify-content` puts it, which defaults to the start.

**What made this survive reading:** `.kb-ghost-link` asked for exactly the right
thing — `display: block; text-align: center` — and never applied, because
`a.kb-ghost-btn` carries an element *and* a class (0,1,1) where that rule
carries only a class (0,1,0). The sheet was asserting something untrue about
itself.

Fix: `justify-content: center` on the rule that actually wins, and the two dead
declarations removed so the sheet stops describing a layout it was not
producing. Verified at 280/320/420/560px — all four controls centre to the
pixel, with identical box widths. The regression test asserts the **cascade**
(if the winning rule makes it a flex container, that rule owns the centring),
not a string; a spot-check for `text-align: center` is exactly what passed while
the link was 104px off.

## Feedback 5 — the emoji picker did not close

> "clicking into the chat box usually closes the emoji menu i feel like, having
> to specifically click the emoji button again felt odd"

**14. Root cause.** The picker had **no dismissal at all** except the toggle
that opened it. `onPick` deliberately keeps it open — picking several emotes in
a row is the normal case — but nothing handled the user reaching for the
composer, so it stayed up over the conversation while they typed underneath it.

**15. Final behaviour.** It closes on `pointerdown` in the composer, and on
Escape.

**`pointerdown`, not `focus`, and that is the whole subtlety.** `onPick` calls
`inputRef.current?.focus()` after every emote so typing continues where the user
left off. Hanging the dismissal on `focus` would have slammed the picker shut on
the *first* pick and traded one annoyance for a worse one. A programmatic
`focus()` fires no pointer event, so this fires for the human and not for us.

Escape returns early so it cannot fall through to the Enter branch and post a
half-typed draft. Seven tests, including "stays open after an emote is chosen" —
which is the one that fails if anybody moves this to `focus`.

## Feedback 6 & 7 — resize directions and the drag cursor

> "the app is only resizeable on the bottom corners? at least the top corners
> too, if not the 4 sides as well for that imo"
> "didnt realize i could resize cuz the top wasnt letting me"
> "gives a hand icon for draggin the box instead"

These are one defect seen from two sides. The top of the panel is the drag
handle and carries `cursor: grab` — an open hand — so a resize gesture there was
answered with a **move** cursor, and with no grip behind it, nothing happened
either. The tester did not conclude "a direction is missing"; they concluded
Watchside was not resizable.

**16. Before.** Grips rendered: `sw`, `s`, `se` — the bottom edge and the two
bottom corners.

Worth recording: `resizeTo` **already handled `w` and `e`**. Both had simply
never been given a grip, so two of the four sides were unreachable code that no
test noticed. The existing fuzz test iterated a hand-written list of five edges,
which is precisely why. It now iterates `RESIZE_EDGES`.

**17. After.** All eight: `n`, `ne`, `e`, `se`, `s`, `sw`, `w`, `nw`.

**18. Top/left geometry.** `resizeTo` was rewritten symmetrically. The invariant
it turns on is the **anchor**: pulling north or west changes size and origin
together, and the opposite edge must not move by a pixel — including after the
size bottoms out and the pointer keeps travelling, which is exactly where naive
geometry drifts.

Containment is applied as a cap on the **size**, not as a correction to the
position, which is what keeps the anchor honest: dragging north past the window
becomes "as tall as the space above the bottom edge allows", never "the panel
jumped". The origin then absorbs whatever the size could not.

**19. Bounds and persistence.** Preserved and tested: `MIN_WIDTH` 280,
`MAX_WIDTH` 560, `MIN_HEIGHT` 340, `MAX_HEIGHT` 1400, viewport containment,
`clampLayout` as a final safety net, integer coordinates, persisted geometry
round-tripping through `serializeLayout`/`parseStoredLayout` unchanged,
collapsed state and reopening untouched. Tests cover:

- every edge × five extreme pointers × three viewports, asserting that any edge
  the gesture is *not* pulling comes back bit-identical;
- a 120-step drag replayed one pixel at a time landing exactly where the
  single-step version lands (no creep while the mouse is held still);
- the minimum-size case for both north and west, which is where drift appears
  and nowhere else. Verified by mutation: replacing the anchor arithmetic with
  the naive `top + dy` fails that test and only that test.

**20. Drag cursor, before and after.** Before: the header's `grab` reached the
very top edge, so the top of the panel said "move me" to a resize gesture.
After: a 6px north strip sits above the header on `z-index` and shows
`ns-resize`; the rest of the header still drags with `grab`/`grabbing`, and its
buttons are still `pointer`.

**21. Resize cursors.** `n`/`s` → `ns-resize`; `w`/`e` → `ew-resize`; `nw`/`se`
→ `nwse-resize`; `ne`/`sw` → `nesw-resize`. Verified by hit-testing every edge
midpoint in Chrome and reading the computed cursor at the element actually under
the pointer.

**A regression this pass introduced and caught.** Measuring rather than assuming
found that the new north-east grip covered the collapse button's corner: **42 of
that button's 576 pixels** answered a resize gesture instead of a click. Header
buttons now outrank the grips (`position: relative; z-index: 4`), taking it to
3px — which is the button's own rounded corner. A control beats a grip.

**Also measured, and left alone honestly:** the panel's 18px border-radius means
the outermost ~5px of each corner is not hittable (corners become grabbable 5–6px
diagonally in). This is pre-existing, unchanged, and reported rather than fought
— enlarging the corner grips would take more of the header.

Corner hint marks now appear on all four corners, since discoverability was the
actual complaint.

## Feedback 8 — wordmark legibility

**22. Root cause.** The report said the wordmark was hard to read *"beside an
icon with substantially stronger visual definition"*. That comparison was the
diagnosis.

The icon is a solid **#A855F7** — the brand accent, straight. The wordmark was
the only thing in Watchside filled with a **gradient**, of two **darker**
purples, through `background-clip: text`. One lockup, painted by two different
rules, and the word came off worse.

`--kb-gradient` exists to be a *background* with white text on top, which is why
both its stops are deep. Filling text with it inverts the requirement.

**23. Treatments evaluated.** Measured at the real rendered size — 13px, weight
800 — by sampling the pixels that actually carry ink, in Chrome, at three device
scales. Median contrast against the panel ground:

| treatment | token contrast | rendered median | verdict |
|---|---|---|---|
| current `#9333ea → #6d28d9` | 3.46 / **2.62** | **2.44:1** | fails; dimmer toward the end of the word |
| solid `--kb-accent` `#a855f7` | 4.70 | 4.02:1 | passes tokens, median short of 4.5 |
| gradient `#c084fc → #a855f7` | 7.04 / 4.70 | 4.80:1 | passes, but needs a second gradient |
| **solid `#c084fc`** | **7.04** | **6.18–6.98:1** | **chosen** |

13px at weight 800 is **not** "large text" under WCAG (that needs 18.66px bold),
so the floor is 4.5:1 — and the old treatment was under even the 3:1 large-text
floor at its dim end.

**24. Final treatment.** Solid `--kb-accent-bright: #c084fc`, a new token.
Rendered ink contrast **2.25–3.40 : 1 → 6.18–6.98 : 1** across device scales
1.0/1.25/1.5.

Three deliberate choices:

- **Solid, not a brighter gradient.** A 135° gradient across 70px of text was
  never visible as a gradient; all it did was make the end of the word dimmer
  than the start. Going solid also keeps `brandAssets.test.ts`'s
  *one-accent-gradient* rule intact — a second gradient token would have cost
  that, and the rule is worth more than the effect. **That test is unmodified
  and still green**; the implementation changed to satisfy it, rather than the
  test changing to permit the implementation.
- **Colour alone.** No stroke, no shadow, no size or weight change. Colour
  clears the floor with room to spare; at 13px a stroke thickens stems into mud
  and a shadow only adds a second dim copy; the weight is already 800.
- **Brighter than the accent, on purpose.** The icon is a 24px shape with large
  filled areas and carries `#a855f7` well. This is a 13px glyph whose stems are
  one or two antialiased pixels wide. Thinner ink needs more luminance to read
  as the same colour. Hue is within 8° of `--kb-accent`, asserted by test.

**Limitation, stated plainly:** Firefox could not be verified directly — headless
Firefox will not rasterise on this machine (`RenderCompositorSWGL failed mapping
default framebuffer`), and two workarounds (screenshot, local reporting server)
both failed. This is reported rather than papered over. Mitigating facts: the
new treatment is a plain `color`, the most cross-engine-safe text treatment
available, and dropping `background-clip: text` *removes* the one genuinely
engine-dependent thing about the old rendering. The contrast arithmetic is
engine-independent.

## Feedback 9 — text size

**25. Previous typography architecture.** There was none to speak of: 108
hard-coded `font-size: Npx` declarations across 14 distinct values, with
`.kb-root` setting a 13px base that most elements overrode.

**26. Options implemented.** **Default (1.0) / Large (1.15) / Extra Large
(1.3)**.

No "Small". It was considered and declined: the brief warns against adding sizes
for symmetry, the panel is already compact, and shrinking its text works
directly against the legibility complaints that produced this feature.

**27. Scaling architecture.** Root-level and centralised. Every font-size in the
sheet is now `calc(Npx * var(--kb-text-scale, 1))` — 108 declarations rewritten
mechanically so no surface could be forgotten and none can drift. One number
reaches all of them.

**Text, and nothing else.** Not padding, not gaps, not icon boxes, not hit
targets, not radii, not the panel's own geometry. That is the line between this
and `zoom`: `zoom` gives you a bigger panel rather than more readable text, and
the person who needs 17px type has the same screen they had before. A test
asserts `font-size` is the **only** property the token reaches.

The fallback of `1` is load-bearing — the sheet is also loaded by the Test Lab,
and a stray element outside `.kb-root` would otherwise compute every font-size
to nothing.

**28. Preference storage.** `localStorage`, key `kickback:textSize`, beside the
panel's geometry — deliberately *not* the worker's `chrome.storage.local`
preferences. Worker preferences arrive over the port whenever they arrive; this
is needed during the **first paint**, or every Twitch page load would draw at the
default size and then visibly reflow to the size the reader actually chose. The
person most likely to notice that is the person who turned the setting on.

Cross-tab via `useStorageSync`, exactly as the collapsed flag does. Applies to
Watchside only — it is a custom property on Watchside's own elements inside a
shadow root; `twitch.tv` is not touched. Updates without reload. An unrecognised
stored value falls back to Default rather than throwing, because this is read
while painting; storage being unavailable entirely is also survived.

The control reuses the existing segmented picker used by Presence, rather than
inventing a second idiom for the same shape of decision.

**29. Layout findings at each text size.** Audited in real Chrome through the
Test Lab — real panel, real components, real stylesheet, real layout — with
every element checked for horizontal overflow, clipped text, overlapping
controls and collapsed hit targets.

Ten surfaces (Friends + Gravity + JOIN, 10-friend stress, long names/casing,
Find Friends + Suggestions, Groups, Account/settings/support/delete,
Watching Together + chat, chat + composer + emote picker, long title + category,
empty state) × three sizes × panel sizes from 280×340 to 560×720.

**Two real defects found, both only in the corner where the panel is narrowest
and the text largest:**

- **The streamer tab collapsed to 4px.** At 280px with Extra Large text the row
  came to Friends 84 + Groups 59 + 54 of gap + 24 of padding = 221 of 280, and
  the streamer tab absorbed the shortfall — still in the tab order, still
  carrying a click handler, impossible to see or hit. Fixed with an `em`
  floor (`min-width: 2.6em`) so it ellipses instead: the failure it was built
  for. It now measures 45px there.
- **With that floor in place the row genuinely does not fit**, and "+ Add"
  pushed 19px past the panel's right edge. The row now wraps.

  *Raising `MIN_WIDTH` was the alternative and was rejected explicitly.* 280px
  was chosen deliberately for a cramped laptop, and making every panel wider to
  serve a setting most people never turn on charges the cost to the wrong
  people. Wrapping costs one row of height, only in the corner that needs it.
- **The emote picker was crushed to 12px** around 51px of content — at Extra
  Large in a short panel, at *every* width. Opened deliberately, drawn as an
  empty sliver. `min-height: 7em`. It still yields before the composer; it stops
  yielding past the point where it is still a picker.

  A `min(7em, 30%)` was tried first and **measured worse**: the percentage
  resolves against a parent whose height the flex layout has not fixed, so it
  contributed nothing and dragged the `min()` down, leaving 40px of 51. The
  bound was not needed — chat is the flexible region and yields first.

**Result after fixes: 30 of 30 surface × size combinations clean at 280×340**,
the absolute minimum panel size, and clean at 280/320/560 × default/large/xlarge
in the earlier sweep.

No increase in minimum panel dimensions was required.

## Feedback 10 — Watching Together height and chat separation

**36. Previous behaviour and root cause.** There was **no static height** — the
user's hypothesis was reasonable but wrong. `.kb-room-people` had
`flex: 1 1 auto` and `.kb-chat-log` has `flex: 1 1 0`. Both grow, so the two
**split** the panel's free space, while the roster also kept its own content
height as its flex basis.

Measured in Chrome, 520px session, two people: the roster box was **236px around
46px of names**, and chat got **202px and a scrollbar**. The empty space was not
reserved for anybody. It was arithmetic.

**37. New sizing.** `flex: 0 1 auto` — content-driven. Takes the height of the
people in it, never grows into space that belongs to the conversation, still
shrinks when the panel is short.

| people | panel | text | roster | chat |
|---|---|---|---|---|
| 2 | 520 | default | **53** (was 236) | **387** (was 202) |
| 3 | 520 | default | 78 | 362 |
| 6 | 520 | default | 143 | 297 |
| 30 | 520 | default | 143 | 297 |
| 12 | 340 | default | 119 | 141 |
| 12 | 340 | x-large | 119 | 141 |

**38. Maximum and overflow.** `max-height: min(11em, 35%)`, then it scrolls
internally — which is what `overflow-y: auto` was always for and what a busy
channel now actually reaches.

Both halves of that cap were arrived at by measuring. `em` alone put an Extra
Large roster at 198px of a ~248px budget in a 340px panel, leaving chat 62px —
**the original complaint, reproduced by the accessibility setting**. A
percentage alone would ignore the text size it exists to serve. A pixel constant
would be the hardcoded one-person screenshot this was told not to become. Across
all 13 measured combinations, chat is never smaller than the roster.

**39. Chat flex and scroll.** Unchanged and now the sole flexible region:
`flex: 1 1 0`, `min-height: 0`, `overflow-y: auto`,
`overscroll-behavior: contain`. The basis of zero rather than auto is
pre-existing and deliberate — with `auto` the log claims its full content height
first and squeezes the composer out of the panel.

**40. Separation.** A hairline `border-bottom: 1px solid var(--kb-line)` plus
6px of padding under the roster. Asked for directly, and worth more now that the
edge moves with the participant count.

**41. Collapse chevron.** It was the literal characters **U+2303 / U+2304** (UP
and DOWN ARROWHEAD) at `font-size: 10px` in `--kb-faint`. Two problems at once:
those code points are absent from most UI font stacks, so what actually drew
them was whatever fallback the browser found at whatever weight it happened to
have; and `--kb-faint` measures **3.56:1** against the panel — the bare floor
for a graphical control and nothing more.

Now an SVG path (`ChevronIcon`, same idiom as every other icon in the set) at
14px in `--kb-dim`, **6.88:1** — the same colour as the label beside it, so the
control and its name read as one thing. A path cannot fall back to a different
font and keeps its stroke weight at any size. Hit target is the whole
`.kb-session-people` button, which is full-width and unchanged; the button
already carried `aria-expanded`.

**42. Under larger text.** The `em` cap means the roster's ceiling grows with
the rows, so the second person does not disappear behind a scrollbar the moment
somebody turns the setting on; the 35% keeps chat larger than the roster at
every size. Verified at Extra Large in the table above and in the 30/30 sweep.

## Feedback 11 — the toolbar badge read as notifications

**43. Current semantics.** The collapsed launcher shows one of two things:
`view.unread.length` (friend requests, gatherings forming) in a purple badge, or
`friendsHere.length` (friends watching the same channel) in a green badge. Never
both.

**44. Why it read as notifications.** A small numeric bubble on a top-nav
control means "this many things are waiting for you" — that is what every other
control up there means by it, Twitch's included. Passive friend presence was
borrowing that language, and the tester read it exactly the way the convention
told them to.

**One discrepancy worth recording rather than smoothing over:** the report
describes the badge as *purple*, and the presence badge is green — purple is the
**request** badge, which is a genuine unread count and correctly numeric. So the
supplied screenshot may have shown the badge working as intended. The fix holds
either way, because a green numeric bubble in a top nav reads as a count of
things too.

**45. Alternatives considered.** (1) remove the count entirely; (2) non-numeric
presence indication; (3) move the count into the panel; (4) reserve numeric
semantics for genuinely attention-requiring state. **No new notification system
was created and no urgency was invented** — the distinction already existed in
the state, and the code even said so in a comment: *"Unseen, actionable things
only. A friend changing channel is not news."*

**46. Final treatment.** (2) + (4), which is also the simplest. `unread` keeps
its number. Presence becomes a 10px dot in `--kb-here`, the same green presence
uses everywhere else in Watchside.

The count is not lost. It moved to the launcher's `title`, which is also the
button's **accessible name** — previously the fixed string "Open Watchside"
regardless of what the badge showed. A screen reader now gets "Open Watchside ·
2 friends here" or "· 1 waiting", which is more than the numeral ever conveyed.
"Waiting" rather than "unread", deliberately: calling them unread would
reintroduce the notification reading the numeral was removed for.

Nothing had covered this badge at all, which is how the semantic could drift. It
is covered now, including that the two states are mutually exclusive.

# Part 2 — accessibility (section L)

**30. Keyboard and focus findings.** Probed live in Chrome across four
surfaces — focusing every focusable element in turn and reading what actually
changed — rather than reasoned about.

**Most of what the probe flagged was the probe being wrong, and each was
verified rather than "fixed":**

| flagged | verdict |
|---|---|
| `kb-join` not keyboard-reachable | **false.** It was the SEND button, `disabled` because the draft was empty. A disabled button correctly cannot take focus. |
| `kb-composer-input` no focus ring | **false.** Border goes `rgba(255,255,255,0.09)` → `rgba(168,85,247,0.55)`. The probe caught a 0.12s transition mid-flight. |
| `kb-emote-search` no focus ring | **false.** It was already focused — the picker autofocuses its search box on open. |
| `kb-search` no focus ring | **false.** Same transition artifact. |

Genuine findings: no keyboard traps, no positive `tabindex` anywhere, sensible
focus order, Enter/Space activation via native buttons, and Escape now dismisses
the emote picker (added in Feedback 5, the one conventional dismissal that was
missing).

**31. Semantic / ARIA findings.** Two real ones, both "state is drawn but not
announced":

- **The presence picker** (Visible / Hide activity / Invisible) conveyed the
  selection only through a CSS class. Now `aria-pressed`.
- **The gathering-alerts switch** put its state entirely in a class on a span

# Part 5 — native-integration exploration (analysis only)

*No architecture was changed. This did not affect v0.9 scope.*

**67. Current Twitch integration architecture.** Recovered from the source, not
assumed.

- **Entry point.** There is **no top-nav injection.** This corrects the premise
  in the brief and matches the Feedback 11 finding: what looks like a top-nav
  entry point is Watchside's own collapsed launcher, a floating button whose
  *default* placement is just below Twitch's nav. It is inside Watchside's own
  layer, not inside Twitch's DOM.
- **Mounting.** One `<div>` appended to `document.body` with
  `position: fixed; inset: 0; overflow: visible; pointer-events: none;
  z-index: 2147483000`, carrying an open shadow root. The layer ignores pointer
  events entirely — only the panel inside it accepts them — so Twitch behaves as
  if Watchside were not there.
- **Styling.** Entirely inside the shadow root, every selector namespaced under
  `.kb-root` and prefixed `kb-`.
- **Writes to Twitch's DOM.** Exactly one, ever: `document.body.appendChild(host)`.
  Verified by grep across `src/platforms/twitch/` and `src/content/`. Nothing
  else is inserted, moved, restyled, or class-marked.
- **Reads of Twitch's DOM.** Three, all advisory:
  1. `anchor.ts` — the bottom of the top-level `<nav>`, polled at 1s, clamped to
     a third of the viewport, falling back to 58px. Feeds the *default* top
     offset only.
  2. `chatRail.ts` — the chat rail's width via Twitch's own `data-a-target` /
     `data-test-selector` hooks (chosen over class names, which are
     styled-components hashes like `Layout-sc-1xcs6mc-0 kaoNZj`), sanity-checked
     against the viewport because a logged-out page lays the rail out at
     `x === innerWidth` while still reporting 340px. Feeds the *default* right
     offset only. Its own comment states the rule: *"Twitch's markup is not a
     contract."*
  3. `navigation.ts` — SPA navigation, handled without touching Twitch's router:
     the URL polled at 400ms, `popstate`, and a `MutationObserver` on `<title>`.
     Channel and title are tracked separately because Twitch sets the URL before
     the title.
- **Drag and resize.** Entirely self-owned; geometry in `localStorage`, clamped
  to the viewport, shared across tabs via the `storage` event.
- **Theater mode.** No special handling and none needed — the panel floats over
  it, and the nav measurement falls back when `<nav>` is absent.
- **Fullscreen.** `host.style.display = document.fullscreenElement ? 'none' : ''`
  on `fullscreenchange`. Watchside gets out of the way.
- **Collapsed chat.** Only affects the *default* placement; a wrong answer costs
  a slightly worse first position, which the user can drag.
- **Viewport changes.** `window.resize` re-clamps; a self-healing
  `MutationObserver` re-appends the host if Twitch's router ever removes it.

**68. Options evaluated.**

**Option A — keep the floating panel.**
*Strengths:* the DOM coupling is essentially zero — one append, three advisory
reads, no writes. Shadow DOM means Twitch CSS cannot reach in and Watchside CSS
cannot leak out. Survives any Twitch redesign by construction: the worst case is
a slightly wrong *default* position. Free-form drag/resize, works identically in
theater mode, trivially disabled in fullscreen. Maintenance burden is close to
nil.
*Weaknesses:* it reads as an application floating **above** Twitch rather than
part of it. It can overlap content the user wants. Discoverability of its
affordances is not free — Feedback 6 is exactly that, and Feedback 11 is a
consequence of floating next to Twitch's nav while not being in it.
*Why chosen originally:* recoverable from the code comments — the pointer-events
layer exists so *"Twitch behaves exactly as if Watchside were not here, while the
panel is free to be dragged anywhere rather than being pinned to one edge."*

**Option B — more native entry point, same floating panel.**
Keep the architecture; make the entry point, opening transition, default
placement and visual relationship feel like they belong. Concretely available
without new DOM coupling: default placement that aligns to the chat rail's edge
rather than merely avoiding it (the measurement already exists); an opening
transition that reads as expanding *from* the launcher; borders/radii/elevation
that echo Twitch's own surfaces; a launcher that visually sits in the nav's
rhythm.
**This captures most of the perceived-nativeness gain at near-zero
architectural risk** — every input it needs is already measured, and nothing new
is written into Twitch's DOM.

**Option C — docked into Twitch's layout.**
Occupying or splitting the right-hand chat region would require *writing* to
Twitch's DOM: inserting into the chat column, restyling its container,
constraining its width, and observing its mutations to survive re-renders. That
inverts the current trust and fragility model in one step. Shadow DOM isolation
for Watchside's own content could be preserved, but the *container* would have
to be Twitch's, so the isolation stops at the boundary that matters. Twitch is a
React SPA that re-renders the chat column on channel change, theater toggle and
rail collapse; every one becomes a re-attachment case. Theater and fullscreen
become special cases rather than non-cases. Small viewports become a negotiation
with Twitch's own breakpoints. Panel resize turns into resizing *Twitch's*
layout. The text-size setting stops being self-contained, because the container
is no longer ours.

**Option D — docked and floating as user-selectable modes.**
This is Option C plus the obligation to keep Option A working, and to keep every
feature working in both. Two layout models, two sets of edge cases, two places
every future feature must be verified — for a preference most users would set
once. On current evidence this is **unnecessary complexity**, not useful
flexibility.

**69. DOM / maintenance-risk comparison.**

| | writes to Twitch DOM | reads relied on | breaks when Twitch changes | recovery |
|---|---|---|---|---|
| **A** | 1 (own host) | 3, all advisory | default *placement* only | user drags it |
| **B** | 1 (own host) | 3–4, all advisory | default placement/alignment only | user drags it |
| **C** | many, structural | container identity, layout, lifecycle | panel misplaced, duplicated, or gone | none automatic |
| **D** | as C | as C | as C, in one of two modes | as C |

**70. UX comparison.** A is the most robust and the least native-feeling. B is
meaningfully more native for a fraction of C's cost — and notably, the two
complaints that motivated this exploration (resize discoverability, badge
semantics) were **both fixable inside A**, and were fixed in this pass. That is
evidence about where the perceived-nativeness gap actually lives: it was in
affordances and visual language, not in the panel being a panel. C is the most
native and the most fragile; D is C's fragility plus double the surface area.

**71. 7TV / BTTV / FFZ compatibility.** *Reasoned from architecture; no
compatibility is claimed without evidence, and none of the three has been tested
against.*

Those extensions work primarily by **replacing or augmenting Twitch's chat
renderer** and injecting controls into Twitch's chat input bar and settings
menus. Collision surfaces and Watchside's current exposure to each:

| surface | current exposure |
|---|---|
| Twitch DOM injection | **minimal** — one appended element under `document.body`, not inside any region they modify |
| chat replacement | **none** — Watchside never reads or writes Twitch chat messages or its input bar |
| CSS | **none in either direction** — shadow root, plus `kb-` namespacing |
| toolbar controls | **none** — no injected nav or chat-bar controls |
| Shadow DOM | Watchside owns its own; it does not enter theirs |
| layout manipulation | **read-only** — rail width is *measured*, never set |
| mutation observers | Watchside observes only `<title>` and its own host's connectedness, never Twitch's layout |

The one realistic interaction under Option A is `chatRail.ts` measuring a rail
that another extension has resized or restyled — which affects only the default
placement and is already sanity-checked. Under **Option C** every row above
becomes a genuine contention point, because Watchside would be competing for the
same chat container those extensions modify. That is a strong independent
argument against docking.

**72. Security / policy implications.**

| | content-script trust boundary | reliance on page DOM | page-controlled data exposure | permissions / hosts / scopes | G7 |
|---|---|---|---|---|---|
| **A** | unchanged | 3 advisory reads | none — nothing read from the page is rendered as content | none | no change |
| **B** | unchanged | same, possibly one more advisory read | none | none | no change |
| **C** | **materially weakened** — Watchside would render inside a container the page controls, and would consume page-derived structure as layout input | structural and load-bearing | **new** — page-controlled values become inputs to rendering; needs explicit treatment as untrusted | none *required*, but the DOM-trust story changes | **would need re-examination**: docking into Twitch's own chat surface changes how Watchside presents itself relative to Twitch Content and Twitch's UI |
| **D** | as C | as C | as C | as C | as C |

No such change was made. This identifies implications only.

**73. Recommendation: B — NATIVE ENTRY-POINT POLISH.**

Keep the floating panel. Its DOM coupling is close to zero and that is the
single biggest reason Watchside is not broken by Twitch redesigns. Invest in the
entry point, opening transition, default alignment and visual relationship,
which is where the perceived gap actually lives — demonstrated by this very
pass, where two of the "doesn't feel native" symptoms turned out to be a missing
grip and a misused badge convention, both fixed without touching the
architecture.

**Not C or D**, and the deciding argument is not effort: docking would invert
the trust boundary, put Watchside into direct contention with the exact chat
region 7TV/BTTV/FFZ modify, and require re-opening G7 — for a gain that is
mostly aesthetic and partly achievable under B.

**74. Roadmap placement.** Not applicable (recommendation is B). B's items are
small, independent, and belong **after** v0.9 ships and after G7 closes — none
