## 3. Invite URL contract

| Hop | URL | Read by |
| --- | --- | --- |
| 1 | `https://anoteroslabs.github.io/kickback/invite?c=CODE` | the landing page |
| 2 | `https://www.twitch.tv/?kickback_invite=CODE` | Kickback's **existing** content script |

**Code format:** 22 characters of `0123456789ABCDEFGHJKMNPQRSTVWXYZ` — the
friend-code alphabet, without `I`, `L`, `O` or `U`, so a code read aloud cannot
become a different valid code. `src/core/invites.ts` is the single source of
truth and `codeFromUrl` accepts both parameter names, so one function answers
for both hops.

**Why two hops.** A content script on the landing page means a new host
permission, shown to the user as *"read your data on that site"*, for one
string. Sending people onward to Twitch means the code is read where Kickback
already runs.

## 4. Attribution continuation

```
Copy invite link            my_invite_code()  → durable code, one per person
   ↓ shared however they like
landing page                ?c=CODE
   ↓ Install Kickback
Chrome Web Store            no code involved
   ↓ Continue with Twitch
twitch.tv/?kickback_invite=CODE
   ↓ content script          codeFromUrl()
worker holds it             session memory only, unclaimed
   ↓ Twitch OAuth
claim_invite(code)          → 'attributed'
   ↓ they become friends     create_friendship() → settle_referral()
   ↓ they open any stream    apply_destinations() → activation stamped
referral succeeds           → award_referral_badges()
```

The code is held **in worker memory only** and never persisted: an unclaimed
code is worth nothing, and storing somebody else's identifier for no benefit is
the wrong trade. The cost is that a browser restart between landing and sign-in
loses it — re-opening the link fixes it, and the common ordering avoids it
anyway because sign-in happens on Twitch, right where the code was picked up.

## 5. Badge presentation

### Shipped: discovery and equipping, in the account panel

`BadgeShelf` sits above the version line in the account card — where a person
already goes to see who they are in Kickback, rather than a screen nobody opens
twice. A row of chips: icon, name, tap to equip, tap the equipped one again to
show none.

- **Earned only.** The list comes from `my_badges()`; there is no local
  catalogue, so an unearned badge is not reachable in the UI at all — and the
  server refuses one anyway (`42501`).
- **No badges, no section.** No empty state and no "keep going" nudge.
- **Heading reads "Kickback badges."** The moment a second issuer exists that
  distinction has to already be on screen rather than retrofitted. Nothing here
  reads Twitch badge data, and no scope was added.

### ⚠ Blocked: badges beside *other people's* names

The requirement *"equipped badge appears on chosen social surface"* is **not
met for other users**, and the reason is structural:

- `user_badges` **is** readable by friends and shared-group members — that
  policy already exists;
- `user_preferences`, which holds `displayed_badge_key`, is **self-only**
  (`0002_policies.sql:124`).

So the client can see *which badges a friend holds* but not *which one they
chose to show*. Rendering the highest-ranked one instead would make the equip
control meaningless, which is worse than not shipping it.

**Closing this needs a schema change**, and the brief says stop before making
one. The smallest fix is a policy widening in a new migration:

```sql
-- 0027, if authorised: a friend may read which badge you chose to show,
-- and nothing else about your preferences.
create policy user_preferences_badge on public.user_preferences
  for select to authenticated
  using (public.is_friend(user_id) or public.shares_group_with(user_id));
```

That is not safe as written — it would expose **every** preference column,
including presence visibility. The correct shape is a narrow
`SECURITY DEFINER` function returning only `(user_id, displayed_badge_key)` for
people the caller may already see. **Roughly twenty lines, one migration, your
call.**

**What this means for the beta:** you can earn a badge, find it, and equip it.
Your friends cannot see it yet.

## 7. Badge earning feedback

**Deliberately minimal, and honestly so.**

The referral count in the invite section is the feedback: *"2 friends have
joined through your link."* A person who sees that and opens the account panel
finds the badge waiting.

**No NEW indicator was added.** Doing it properly means persisting
last-seen-badge state across worker restarts and reconciling it with awards that
happen while the panel is closed — real complexity for a small nudge, and the
brief says if it adds disproportionate complexity, simply make earned badges
easy to find. They are: the account panel is one click from the panel header.

Not built, per the brief: unlock animation, reward ceremony, rarity,
marketplace, XP.
