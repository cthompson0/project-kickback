## 2. P0-1 — the invite page offers both browsers · **LIVE**

**The defect.** The page every invite link lands on contained **zero references
to Firefox or Mozilla** and no UA detection — a hardcoded Chrome store URL,
steps naming the Chrome Web Store, a footer calling Watchside "a Chrome
extension". Firefox was, and is, the only build a person can actually install.
So an invited Firefox user was told to install something they could not, on the
single path a stranger with no Watchside friends has to a first connection.

**The fix.** Both stores are plain anchors with working hrefs rendered *before*
any script runs. Detection is decoration: it adds a hint beside the matching
browser and **cannot hide the other**, so a spoofed agent or an unanticipated
browser still leaves two working choices. No tracking was added — the user agent
is read and discarded. Nothing stored, nothing fetched, no-referrer preserved,
invite code untouched.

**Honesty about compatibility.** Mobile is told Watchside is a desktop
extension. Desktop Safari gets a *different* sentence, because telling a
computer to "open this on a computer" is not help.

**Deployed independently** to `Anoteros-Labs/anoteros-labs.github.io` (`7f18d3a`)
and **verified live in a real browser**.

**All three invite surfaces now serve both browsers:**

| Surface | Chrome | Firefox | Carries code |
| --- | --- | --- | --- |
| `watchside.app/i/<code>` (canonical) | ✅ | ✅ | ✅ |
| `…github.io/watchside/invite/?c=` (legacy) | ✅ | ✅ | ✅ |
| `…github.io/kickback/invite/?c=` (pre-rename) | ✅ | ✅ | ✅ |

Verified under both Chrome and Firefox user agents; all three land on
`twitch.tv/?kickback_invite=<code>`.

## 3. P0-4 — a budget for search · migration 0041

**Semantics:** `user_search`, **60 per 10 minutes**, per actor, via the existing
`consume_rate_budget` primitive — no new subsystem.

**Calibrated against the client, not guessed.** `FindFriends` debounces at 250ms
with a 2-character minimum, so looking somebody up costs one to four searches.
Sixty is fifteen-to-sixty people in ten minutes: past any real session of adding
friends, far below the thousands enumeration needs. The window is shorter than
`friend_request`'s hour because search is read-only and recoverable.

**Charged after the length check**, so a one-character keystroke cannot burn the
allowance on the way to a real name.

**Exhaustion returns empty, not an error.** The client has always treated
"nothing found" as ordinary; raising would put an error dialog on a keystroke
*and* tell an enumerator exactly where the ceiling is.

**The real change is volatility** — the function was `stable`, which cannot write
a budget row. Same signature, same grants, same results for legitimate callers.
Block semantics are carried through unchanged and retested in both directions.

**13 tests**, covering normal use, exhaustion, per-actor isolation, window
rollover, short-query non-charging, a systematic alphabet sweep, and the
blocked-user invariants. **2 destruction levers.**

## 4. P0-2 — the pending invite survives · in v0.9

**The defect.** The code lived in a bare module-scope variable, justified by *"an
invite arrives on Twitch moments before a sign-in"*. That is wrong in the case
that matters: the recipient is by definition a new user, so between capture and
claim they must find the panel, press Continue with Twitch, read a consent
screen, and approve it — an unbounded user-driven detour, across which MV3
promises nothing. `src/background/index.ts` says so in its own header: *"nothing
here may live only in memory."*

The failure was silent both ways: the recipient arrived with no friend and no
error, indistinguishable from a cold install; the inviter was never told.

**Lifetime semantics:**

| | |
| --- | --- |
| Key | `watchside:pendingInvite` — its own, never the campaign's |
| Stored | one code + capture timestamp |
| TTL | **24 hours** — shorter than the campaign's 7 days, because an invite is a message from somebody you know with a page saying install and come straight back |
| Expiry checked | on the way **in** as well as out, so an invite aged out while the browser was closed never reaches the worker |
| Future-dated capture | refused — a wrong clock would otherwise never expire |
| Cleared on | **any server verdict** (`attributed`, `already`, `self`, `blocked`) |
| **Not** cleared on | network error — a dropped connection used to discard it permanently |
| Idempotency | server-side; `claim_invite` returns `already` for a second attempt, one referral per invitee forever |

**Separate from M5C by construction.** Different key, different RPC, different
TTL. A test asserts the invite binds through `claimInvite` and the campaign
through `bindAcquisition`, so neither can become the other.

**Worker-eviction proof.** The real built bundle is evaluated in a VM sandbox
and its storage reads observed — the same technique `backgroundLifecycle.test.ts`
uses. Against the **pre-fix** bundle and source, **9 of 11 tests fail**,
including the behavioural one, because the old worker never touched the key.

## 5. P0-3 — canonical invite links · in v0.9

`inviteLinkFor` now mints `https://watchside.app/i/<CODE>`.

**Legacy compatibility, proved:** `normalizeInviteCode` still reads the legacy
`?c=` shape, the pre-rename `/kickback/invite/` shape, and the canonical path.
All three live surfaces still resolve (§2).

**One subtlety worth recording.** `codeFromUrl` parses **query parameters only**,
deliberately — it runs on `twitch.tv`, where a channel name is a path segment
too, and matching one against the code alphabet is a risk taken for no gain. So
a *pasted* canonical link is read by `normalizeInviteCode`, which understands the
path. The tests now say which reader answers for which hop instead of implying
one function does both.

**Regression guard:** a test asserts the minted link is canonical, contains no
`github.io`, no `?c=`, and uses `/i/` rather than `/c/` — invitation identity is
not a campaign code.

## 6. P0-5 — the activation denominator · migration 0042

**No telemetry was added, and that was the right call.** Every fact already
exists and is authoritative:

| Fact | Source |
| --- | --- |
| who authenticated | `authenticated_session_started` |
| whether they have a friend | `public.friendships` — the graph itself |
| when the first arrived | `friendships.created_at` |
| what they reached after | events existing since M3A/M5A |

A client event announcing "I am in the zero-friend state" would be a *worse*
source: it would go missing in exactly the case being measured — a browser closed
in disappointment thirty seconds after install. **The absence of a friendship row
IS the state**, and an absence cannot fail to be recorded.

**`activation_actor_v`** — one row per non-internal actor who ever authenticated.
**`activation_funnel_v`** — every stage divided by **all** of them, never by the
survivors of the stage before. If the first edge fails, `friended_rate` falls and
every rate below falls with it.

**M3D semantics borrowed, not restated.** The social-JOIN definition comes from
`m3d_social_joins_v`; a test reads the view definition to prove it. Another
proves the funnel never touches `acquisition_attribution` — activation answers
*"did they reach value"*, acquisition answers *"how did they arrive"*.

**Adversarial proof.** Four users authenticate; one makes a friend and sees a
gathering; two churn silently having emitted one event in their lives. The funnel
reports **one in four**, not one in two. A stage-over-previous-stage funnel would
have reported 100%. **3 destruction levers**, including one that restricts the
denominator to users who already have friends.

Rates are NULL below three actors, matching 0035/0038/0040.
