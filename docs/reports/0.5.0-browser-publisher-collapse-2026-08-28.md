**Date:** 2026-08-28

**Version:** 0.5.0, unchanged
**Hosted analytics schema version:** **25** — unchanged, and **no migration is required**

**No SQL was written, changed or applied.** No migration was created. No server

## 1. Hard browser and hosted evidence

Supplied by the owner, from two accounts with several Twitch streams open in
separate tabs, read directly out of hosted Supabase while the tabs were open:

> `presence_destinations` = **exactly 1 row**, for **both** accounts.

That is authoritative and it is what this investigation started from. It rules
out the read path by construction: with one row in the table there is nothing
for `list_friend_destinations`, the client state, Gravity or the panel to get
wrong. The collapse is at or before the write.

**The previous fix was real but incomplete.** It removed the double-write race
and the thirty-minute decay, and those defects were genuine — the PGlite tests
that reproduce them still pass. It did not address the defect below, which
produces the identical symptom by a completely different mechanism, and which
no test in the repository was shaped to catch.

## 2. Actual root cause

> **An MV3 service worker is evicted routinely. Eviction destroys the module
> scope that holds the tab registry, so the revived worker knows about no tabs
> at all. Every content script reconnects its port transparently — and then says
> nothing. The worker learns what a tab is showing from exactly one `activity`
> message, and the content script only sends that on mount, on navigation, on
> `visibilitychange`, on `pageshow` and when the title settles. A tab sitting
> quietly in the background produces none of those, so the revived worker never
> finds out it exists. Only the tab the user touched next was ever
> re-registered — and one tab means one destination.**

Three files, and the gap between them:

**`src/client/port.ts`** reconnects, and sends nothing but `hello`:

```ts
port.onDisconnect.addListener(() => {
  port = null
  failPending('Kickback lost its connection. Try again.')
  scheduleReconnect()
})

send({ type: 'hello' })
```

**`src/content/index.tsx:106-124`** reports activity on five occasions, none of
which is a reconnect:

```ts
send()                                              // mount, once
watchChannel(send)                                  // SPA navigation
document.addEventListener('visibilitychange', send)
window.addEventListener('pageshow', send)
watchTitle(...)                                     // title settling
```

**`src/background/index.ts:1708-1711`** registers the port but not the tab:

```ts
if (port.name !== PORT_NAME) return
ports.add(port)
```

`tabActivity.update(port, …)` happens **only** in the `activity` message
handler. So a port can be connected and completely unknown to the registry —
and that is the steady state after every eviction.

### Why it presents as exactly one row rather than zero

After eviction the presence reporter is also fresh (`published = null`), so
nothing is written until some tab reports. The next thing the user does is look
at a tab, which fires `visibilitychange` in it. That one tab registers,
`destinations()` returns one channel, and `report_destinations(["that_one"])`
writes exactly one row. It then stays there, because the reporter correctly
skips writes when the set has not changed.

### Why every test passed

`destinationPublishing.test.ts` drove `createActivityRegistry` directly and
never modelled port death. `multiDestination.test.ts` tests the registry alone.
The PGlite suites test the server. **Nothing in the repository exercised the
port lifecycle**, which is exactly where the defect lives. That gap is closed by
§9.

## 4. Real runtime port topology

Traced through the actual bootstrap, not the tested model.

| Question | Answer |
| --- | --- |
| Ports with 3 Twitch tabs open | **3.** One per tab. `createPortClient()` runs once per content-script mount. |
| Same service worker instance? | **Yes.** One worker per extension; `chrome.runtime.onConnect` is a single listener. |
| Ports retained in a collection? | **Yes** — `const ports = new Set<chrome.runtime.Port>()` (`index.ts:1220`). |
| Channel state per port or global? | **Per port.** `Map<object, TabRecord>` keyed by the `Port` object itself. No global `currentChannel` field controls the publisher; `currentChannel()` is a *derived* getter over `effective()`. |
| Does a later port overwrite earlier state? | **No.** Distinct keys. |
| Is the worker restarting and rebuilding only one destination? | **YES. This is the defect.** |
| Does only the visible content script send its channel? | Not by design — but **after a restart, in effect yes**, because only a tab that produces an event re-reports. |
| Do hidden tabs stop reporting or disconnect? | They neither disconnect nor report. They stay connected and silent, which is the worst case here. |
| Does SPA navigation replace ports? | **No.** Twitch is a SPA; the content script and its port survive navigation, and `watchChannel` re-reports. |
| Is the content script injected on all Twitch tabs? | **Yes** — `https://www.twitch.tv/*` and `https://twitch.tv/*`, `document_idle`. |
| Do the match patterns allow every stream tab? | **Yes.** A stream page is `twitch.tv/<channel>`. |
| Is the registry used in tests wired into production? | **Yes** — one `createActivityRegistry()` at `index.ts:364`, fed only from the `activity` handler. The tests instantiate the same factory; what they did not reproduce was the *lifecycle*. |

### The topology that actually produced one row

```
worker alive     port1→stream_a  port2→stream_b  port3→stream_c   registry: 3   publish: [a,b,c]
                          │
             MV3 evicts the worker (~30s idle)
                          │
worker gone      all 3 ports disconnect; module scope destroyed
                          │
             all 3 content scripts reconnect (500ms backoff)
                          │
worker revived   port1' port2' port3' connected — and SILENT   registry: 0   publish: —
                          │
             user looks at one tab → visibilitychange → 1 activity
                          │
worker revived   registry: 1   publish: ["that_one"]   →   presence_destinations = 1 ROW
```

## 8. Fix

### The fix itself — `src/client/port.ts`

The tab remembers the last activity it reported and **replays it on every
connect**:

```ts
/** The last thing this tab told the worker it was showing. */
let lastActivity: ClientMessage | null = null

function connect(): void {
  ...
  send({ type: 'hello' })
  // And say where we are again, because the worker has forgotten.
  if (lastActivity) send(lastActivity)
}

reportActivity: (channel, visible, channelName) => {
  lastActivity = { type: 'activity', channel, visible, channelName: channelName ?? null }
  send(lastActivity)
},
```

Three properties worth stating:

- **The tab is the authority.** It knows its channel and its visibility; the
  worker is entitled to ask again by simply losing its memory. Replay is the
  honest expression of that.
- **It cannot go stale.** Navigation and visibility changes both go through
  `reportActivity`, so `lastActivity` is by construction the tab's current
  truth — including a tab on twitch.tv itself, which replays `channel: null`.
- **It is ordered after `hello`,** so the state snapshot the worker sends back
  is not racing a registry update.

**No new message type, no protocol change, no worker change required.** Nine
lines in the client.

### Development diagnostics — required by the brief, and dev-only

Behind the existing build-time constant (`VITE_KICKBACK_ENV !== 'production'`),
the same one `kickbackMetadata` and `kickbackSession` already use, so a
production bundle folds it away entirely.

- **`activity.ts`** gains `snapshot(): TabSnapshot[]` — read-only, returns every
  live tab with its port key, channel, visibility and both timestamps. This is
  what makes "the worker has forgotten this tab" observable at all.
- **`index.ts`** gains `watchPresenceWrites(backend)` — a pass-through that
  records and `console.info`s every `report_destinations`, `report_presence` and
  `report_offline` with an ISO timestamp and the exact payload, keeping the last
  40. **It returns the backend object untouched in production**, so the thing
  being observed is the thing that ships. Heartbeats are deliberately not
  recorded; they would drown the other three.
- **`index.ts`** gains `portLabels` — a `WeakMap` giving each port a stable
  `tab1`/`tab2`/`tab3` name so diagnostics can name a tab instead of printing an
  object. A `WeakMap`, so naming a tab cannot keep a closed one alive.
- **`index.ts`** gains the `kickbackDestinations` console surface (§12).

**Privacy:** channel names appear in this development console surface and
nowhere else. Nothing here reaches analytics or failure telemetry, which take a
fixed vocabulary and never a channel. No tokens, no emails, no message bodies,
no friend codes — none of those exist on this path at all.

### What was deliberately *not* changed

- No server SQL. The evidence proves the payload was a one-element array, so the
  server was correct.
- No worker protocol addition. A "worker asks each connecting port for its
  activity" handshake would also work and is strictly larger — a new message
  type, a client handler, and a matching change in `demo.ts`.
- No change to the reconnect backoff. A hidden tab's timers are throttled by
  Chrome, so its replay can take up to about a minute after an eviction. It
  converges, and shortening it would mean fighting Chrome's throttling for a
  case that resolves itself.

## 9. Production-wiring regression test

**`tests/extension/workerPortPublishing.test.ts` — 14 tests.**

This is the test the previous round should have had. It uses the **real
`createPortClient`**, including its reconnect path, three fake `chrome.runtime`
ports, the real `createActivityRegistry`, the real `createPresenceReporter`, and
a `pushActivity` copied verbatim from the worker. The only things mocked are
chrome itself and the network. **The code path that was broken is not mocked
away.**

Critically, the worker is a **factory, not a singleton**, so `evict()` can throw
one away and build another — which is precisely what MV3 does and what no
previous test modelled.

**Verified as evidence: 6 of the 14 fail against the pre-fix `port.ts`**,
including the headline case.

| Group | Tests | Covers |
| --- | --- | --- |
| three tabs through three real ports | 4 | three ports exist; all three aggregated; **all three in the RPC payload**; no singleton write |
| after the service worker is evicted | 6 | **still publishes all three once the tabs reconnect** (the regression); three in the payload after reconnecting; does not publish only the tab that moves next; survives two evictions; replays the *current* channel after navigation, not the opening one; replays a tab on no channel |
| the published set holds still | 4 | survives heartbeats and the 10-minute refresh; survives visibility changes across all three tabs **with zero writes**; survives unrelated port messages (`hello`, `seen`); drops exactly the destination whose tab closed |

### One existing test was tightened, not weakened

`destinationPublishing.test.ts` → "leaves both presence entry points to the
reporter alone" strips the reporter block and asserts nothing else names the
presence RPCs. `watchPresenceWrites` legitimately names both, because it
delegates. Rather than loosen the rule, the wrapper is excluded **by name** and
a **new test** pins it to being a pass-through — `if (!DIAGNOSTICS) return
backend`, and each branch forwarding its arguments unmodified. **Net: one
assertion narrowed by an explicit named exclusion, four assertions added.**

## 13. SQL retest query

Read-only. Replace `'REPLACE_ME'` with the publishing account's **Twitch
login**. Run it only **after** the DevTools check above shows three
destinations, so a disagreement means something.

```sql
select ca.platform_login,
       p.status,
       p.channel                                     as legacy_primary,
       (p.status = 'online' and p.last_seen_at > now() - interval '90 seconds')
         as parent_live,
       (select count(*) from public.presence_destinations d
         where d.user_id = ca.user_id)               as destinations_total,
       (select count(*) from public.presence_destinations d
         where d.user_id = ca.user_id
           and d.last_active_at > now() - interval '30 minutes')
         as destinations_active
  from public.connected_accounts ca
  left join public.presence p on p.user_id = ca.user_id
 where ca.platform = 'twitch'
   and ca.platform_login = lower('REPLACE_ME');
```

```sql
select d.channel,
       d.opened_at,
       d.last_active_at,
       now() - d.last_active_at                          as destination_age,
       d.last_active_at > now() - interval '30 minutes'  as destination_active,
       public.is_present_at(d.user_id, d.channel)        as visible_to_a_friend
  from public.connected_accounts ca
  join public.presence_destinations d on d.user_id = ca.user_id
 where ca.platform = 'twitch'
   and ca.platform_login = lower('REPLACE_ME')
 order by d.last_active_at desc, d.channel;
```

Both queries are executed against the real schema by
`tests/db/destinationCollapse.test.ts`, so the table and column names are known
good.

**`destinations_total` should now be 3 with three streams open.** If DevTools
says three and this says one, that is a genuinely new finding and the server
