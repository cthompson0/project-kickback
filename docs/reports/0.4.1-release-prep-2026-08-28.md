## 2. Version locations changed

The repository already had a single-source convention, and it was followed
rather than replaced.

**Two files hold the number, and `verify:store` already enforced their
agreement:**

| Location | Before | After |
| --- | --- | --- |
| `public/manifest.json` → `version` | 0.4.0 | **0.4.1** |
| `package.json` → `version` | 0.4.0 | **0.4.1** |
| `package-lock.json` → `version` and `packages[""].version` | 0.4.0 | **0.4.1** (via `npm install --package-lock-only`) |

**Everything else derives.** Four build configs read the manifest at build time
and define one constant:

```js
// vite.config.ts, vite.background.config.ts, vite.testlab.config.ts, vitest.config.ts
const version = JSON.parse(readFileSync('public/manifest.json', 'utf8')).version
define: { __KICKBACK_VERSION__: JSON.stringify(version) }
```

`src/vite-env.d.ts` declares it, and `src/background/index.ts`,
`src/testlab/TestLab.tsx` and `src/ui/KickbackPanel.tsx` consume it.

**No second version source was invented.** `__KICKBACK_VERSION__` was already
the mechanism; this release only bumps the number it reads.

### One deliberate non-change

`tests/db/feedback.test.ts` contains the literal `'0.4.0'` four times. That is a
**payload fixture** for the feedback-context whitelist test — an arbitrary
string being checked for round-trip preservation, not a version source. Bumping
it would be scope creep and would make the test look like a version assertion
when it is not.

## 3. How the UI obtains and displays the version

### Where it is

**At the bottom of the account panel**, under Sign out. That is the existing
Settings/About surface — the place presence visibility, notifications, mutes,
blocks, Reset layout and Feedback already live.

```
Kickback v0.4.1
```

### How it gets the number

`src/ui/components/AuthStates.tsx`, in `AccountCard`:

```tsx
<div className="kb-account-version">Kickback v{__KICKBACK_VERSION__}</div>
```

**The build-time constant, not a hard-coded string.** It cannot drift from what
Chrome reports, because both trace to `public/manifest.json`.

### Why the account panel, when a footer already showed it

The panel footer has carried `v0.4.0` for a while, and it is not sufficient: it
is small, at the very bottom, and **it is replaced by the layout hint on a first
run** — precisely the moment a new tester is most likely to be asked what they
are running. The account panel is where somebody looks when a question is about
their own setup.

The footer is unchanged. Two displays of one constant cannot disagree.

### What it deliberately does not show

No diagnostics, no user id, no friend code, no Twitch login, no channel, no
session id, no logs, no tokens. **A test asserts this** — it extracts the
rendered line and checks it equals exactly `Kickback v<version>` and contains
none of the identity values present in the fixture.

Diagnostics belong in Feedback, which assembles them in the service worker from
a server-enforced whitelist and sends them because the user chose to.

### Cost

No new permission. No new dependency. No new page. One `<div>` and a
seventeen-line CSS rule.

## 9. LOCAL MANUAL SMOKE TEST — v0.4.1

Install `releases/Kickback-Private-Beta-v0.4.1.zip` unpacked via
`chrome://extensions` → Developer mode → Load unpacked. **This is the sideload

### A — Version is visible and correct

1. Open the panel on twitch.tv, open the **account panel**.
2. Scroll to the bottom. It reads **`Kickback v0.4.1`**.
3. Confirm the panel **footer** also reads `v0.4.1` — the two must agree.
4. Confirm `chrome://extensions` shows **0.4.1** for Kickback.
5. Confirm the version line shows **nothing else** — no id, no channel, no
   session.

### B — Chat: "You", colors, and following (findings #2, #4, #9)

6. Open a group with **more than 60 messages** of history. It opens at the
   bottom.
7. Your own messages read **"You"**; everyone else reads their Twitch name.
8. Open a **Stream Room** with someone. Confirm the same — "You" for you, names

10. Have the other account send five messages to the group. **Each scrolls into
    view without touching the mouse.** This is the regression that used to stop
    working past 60 messages.
11. Scroll up ten messages. Have them send again. **The view must not move**,
    and **"New messages ↓" must appear.**
12. Click it — jumps to the bottom, control disappears, following resumes.
13. Send a message containing an emote. The view stays pinned after the image

### C — Stream Room surface (finding #10, temporary fix)

15. With a friend on the same channel, exchange messages.
16. Have the friend leave the channel. **The room tab must remain and the

17. Leave it alone past 30 minutes with no new messages — the tab goes on its

### D — Cross-tab panel state (finding #7)

19. Open two Twitch tabs. Collapse the panel in tab A → **tab B collapses.**

21. Drag the panel in A → it moves in B. Resize in A → it resizes in B.
22. Start a drag in A and, without releasing, collapse in B. **A's gesture must

### E — Telemetry is arriving and is clean

23. Use the panel normally for a few minutes; briefly disconnect the network and

## 10. GO / NO-GO — uploading v0.4.1 to the Chrome Web Store after manual smoke

## **CONDITIONAL GO**

Every automated gate passes and the release artifacts are correct. The condition
is the manual smoke pass in §9, and it is a real condition rather than a
formality.

### Why the condition is real

Patch 1's largest change is the chat autoscroll rewrite, on the busiest surface
in the product. Its tests run in jsdom, which has **no layout engine** — they
assert the component's arithmetic against geometry the test supplies. That is
the right way to catch the bug that shipped, and it cannot tell you how
scrolling *feels* in a real browser at a real frame rate. Section B exists for
exactly that gap.

The cross-tab sync is the other one worth watching: it is correct by design, but
a panel that moves or collapses under somebody's cursor in a background tab is a
new behaviour and only real use will say whether it reads as helpful or as
startling.

### Upload when all of these are true

1. **§9 A–F pass**, in particular B (chat follow) and D (cross-tab).
2. **Telemetry is confirmed clean** — §9 step 25. This is the first release
   carrying diagnostics; verifying once that nothing free-form arrives is worth
   more than any amount of code review.
3. **Hosted stays at analytics schema 24.** 0.4.1 needs nothing beyond it, and
   nothing in this pass changed it.

### Then upload, with these already true

- The store package is the correct shape: `manifest.json` at the archive root,
  `key` omitted, version 0.4.1 — verified in §7.
- **0.4.1 > 0.4.0**, which the store requires of every upload.
- The extension identity is unchanged, so **no OAuth redirect work follows** and
  no allow-list entry needs updating.
- No new permission, so **no tester will be prompted to re-accept anything** on
  upgrade — an upgrade that demands new permissions is silently withheld from
  users until they accept, which would be a poor way to ship a fix release.

### NO-GO if

Any §9 step fails; or any diagnostic row contains free-form text; or the
installed version does not read 0.4.1 in both the account panel and
`chrome://extensions`.

### Still outstanding, and none of it blocks this upload

- Add `https://ngfopkeokddfnncdhfkhnffilbdhkkip.chromiumapp.org/` to Supabase →
  Authentication → URL Configuration → Redirect URLs. **Required for sign-in on
  a Store install**, and unrelated to this version bump.
- Capture the listing screenshots (1280×800) and the 440×280 promo tile.
- Delete or sanitize `cthompson0/kickback-public`.

**The redirect allow-list entry deserves emphasis.** It is easy to read the
Store upload as the last step; it is not. A tester installing from the Store
cannot sign in until that URL is on the list.
